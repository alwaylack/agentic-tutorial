# 第 19 章 · 实战一：测试智能体——从需求到测试用例

> 本章目标：综合运用前 18 章所学，构建一条「需求解析 → 需求评审 → 测试方案 → 测试用例生成」的四阶段多 Agent 流水线；用例生成阶段支持参考**交互稿设计图**产出 UI 用例。

## 19.1 目标与总体架构

真实 QA 工作流不是一个大 prompt 能解决的：需求要拆解、评审要把关、方案要定策略、用例要有结构。我们把它建模为**四个专职 Agent 组成的流水线**，每个 Agent 只做一件事：

```text
需求文档(requirements.md)      交互稿设计图(mockup.png)
        │                            │
        ▼                            │
┌──────────────────┐                 │
│ 需求解析 Agent     │ 输出 FunctionalPoint[]（结构化功能点）
└────────┬─────────┘
         ▼
┌──────────────────┐   不通过 → 附评审意见退回人工/重新解析
│ 需求评审 Agent     │ 输出 ReviewResult（通过与否 + 风险）
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 测试方案 Agent     │ 输出 TestPlan（范围/环境/优先级/方法）
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 用例生成 Agent     │◄── 设计图以图片输入注入
└────────┬─────────┘  输出 TestCase[]（含 UI 交互路径）
         ▼
   cases.json（下一章的自动化执行输入）
```

设计原则：

- **单一职责**——每个 Agent 的 systemPrompt 只描述一个角色，模型不串戏；
- **数据契约显式化**——阶段间传递的数据用 `interface` 固定，Agent 输出 JSON 后由代码校验再流转；
- **失败可退回**——评审不通过时流程终止并给出原因，而不是带病往下走。

## 19.2 数据契约：先定义接口，再写提示词

TypeScript 项目的好处是能把"阶段间约定"变成编译期检查。新建 `pipeline/types.ts`：

```typescript
// pipeline/types.ts —— 流水线各阶段的数据契约

/** 需求解析阶段的输出：一条功能点 */
export interface FunctionalPoint {
  id: string;            // 功能点编号，如 F-01
  name: string;          // 功能点名称，如「购物车批量删除」
  description: string;   // 行为描述（做什么、触发条件、结果）
  priority: "P0" | "P1" | "P2";   // 业务优先级
  ambiguities: string[]; // 解析时发现的模糊点（供评审重点检查）
}

/** 需求评审阶段的输出 */
export interface ReviewResult {
  passed: boolean;        // 是否通过评审
  risks: string[];        // 风险清单（如「未定义并发上限」）
  suggestions: string[];  // 改进建议
  blocker?: string;       // passed=false 时的阻断性问题描述
}

/** 测试方案阶段的输出 */
export interface TestPlan {
  scope: string[];          // 测试范围（覆盖哪些功能点 id）
  outOfScope: string[];     // 明确不测的范围
  environment: string;      // 环境，如「staging + Chrome 最新版」
  methods: string[];        // 方法：等价类划分 / 边界值分析 / 场景法 / 错误推测
  focusAreas: string[];     // 高风险聚焦区域
}

/** 一条测试用例 */
export interface TestCase {
  id: string;             // TC-001
  relatedFeature: string; // 关联功能点 F-xx
  title: string;
  precondition: string;   // 前置条件
  steps: string[];        // 操作步骤
  expected: string;       // 预期结果
  priority: "P0" | "P1" | "P2";
  type: "api" | "ui" | "mixed";  // 下一章按此字段路由到接口/Web 执行器
}
```

## 19.3 四个专用 Agent 的定义

每个阶段一个 `Agent` 实例，systemPrompt 聚焦本阶段职责，并**硬性要求输出纯 JSON**：

```typescript
// pipeline/agents.ts —— 四个阶段 Agent 的工厂函数
import { Agent } from "@earendil-works/pi-agent-core";
import { createModels } from "@earendil-works/pi-ai";

const models = createModels();
const model = models.getModel("anthropic", "claude-sonnet-4-6")!;

/** 创建阶段 Agent 的通用封装 */
function stageAgent(systemPrompt: string): Agent {
  return new Agent({
    initialState: { systemPrompt, model, messages: [] },
    streamFn: models.streamSimple.bind(models),
  });
}

// 阶段一：需求解析
export const parserAgent = stageAgent(`你是资深需求分析师。
任务：阅读需求文档，拆解出所有可测试的功能点。
要求：
1. 每个功能点独立成条，编号 F-01 起；
2. description 必须包含「触发条件 + 行为 + 结果」；
3. 发现文档中含糊、缺失、矛盾的点写入 ambiguities；
4. 最终只输出 JSON 数组，不要任何解释文字或 markdown 代码块围栏。`);

// 阶段二：需求评审
export const reviewerAgent = stageAgent(`你是苛刻的测试架构师，负责需求评审。
任务：审查功能点清单的完整性、二义性、可测性。
判定标准：
1. 每个功能点都能直接推导出至少一条测试用例 → 可测；
2. 存在无法量化的描述（如「快速响应」「良好体验」）→ 二义性风险；
3. 缺少异常流/边界条件说明 → 完整性风险。
存在任一阻断性问题则 passed=false 并写明 blocker。
最终只输出 JSON 对象，字段见 ReviewResult。`);

// 阶段三：测试方案
export const plannerAgent = stageAgent(`你是测试策略专家。
任务：根据通过评审的需求和评审意见，制定测试方案。
要求：
1. methods 从等价类划分、边界值分析、场景法、错误推测中选择并说明用于哪些功能点；
2. focusAreas 优先覆盖 ReviewResult.risks 中列出的高风险区；
3. environment 写清被测系统版本、依赖服务、浏览器/客户端要求。
最终只输出 JSON 对象，字段见 TestPlan。`);

// 阶段四：测试用例生成（支持看设计图）
export const caseGenAgent = stageAgent(`你是测试用例设计师。
任务：依据测试方案生成结构化测试用例。
要求：
1. 若提供了交互稿设计图，必须先对照图片提取页面元素、布局与交互路径，
   为每个可点击元素和状态变化生成对应 UI 用例；
2. 正向路径与异常路径都要覆盖（网络失败、空数据、权限不足等）；
3. 步骤要具体到可执行，禁止出现「适当操作」这类模糊表述；
4. type 字段：纯后端逻辑用 api，页面操作用 ui，两者结合用 mixed；
5. 最终只输出 JSON 数组，字段见 TestCase。`);
```

## 19.4 阶段一 + 二：需求解析与评审

流水线编排的核心是：**调用 Agent → 提取纯文本回复 → 解析 JSON → 校验后传给下一阶段**。先写一个通用的「跑一回合拿文本」工具函数：

```typescript
// pipeline/run.ts —— 与 Agent 交互的通用工具
import type { Agent } from "@earendil-works/pi-agent-core";

/** 执行一次 prompt 并收集 assistant 的完整文本回复 */
export async function runStage(agent: Agent, input: string, images?: Array<{ type: "image"; data: string; mimeType: string }>): Promise<string> {
  let reply = "";
  const unsubs = [];
  // 订阅事件流：只在 message_update 里累积 text_delta
  unsubs.push(agent.subscribe((event) => {
    if (
      event.type === "message_update" &&
      event.assistantMessageEvent.type === "text_delta"
    ) {
      reply += event.assistantMessageEvent.delta;
    }
  }));
  try {
    await agent.prompt(input, images);
  } finally {
    unsubs.forEach((fn) => fn());   // 记得取消订阅，避免重复累积
  }
  return reply;
}

/** 从模型回复中安全提取 JSON（容忍偶发的代码块围栏） */
export function extractJson<T>(raw: string): T {
  const cleaned = raw.trim()
    .replace(/^```(?:json)?\s*/i, "")   // 去掉开头的 ```json
    .replace(/```\s*$/, "");            // 去掉结尾的 ```
  return JSON.parse(cleaned) as T;
}
```

接着实现前两个阶段：

```typescript
// pipeline/stages1-2.ts —— 解析与评审
import fs from "node:fs/promises";
import { runStage, extractJson } from "./run.js";
import type { FunctionalPoint, ReviewResult } from "./types.js";
import { parserAgent, reviewerAgent } from "./agents.js";

/** 阶段一：读文档 → 功能点清单 */
export async function parseRequirements(docPath: string): Promise<FunctionalPoint[]> {
  const doc = await fs.readFile(docPath, "utf-8");
  const raw = await runStage(parserAgent, `以下是需求文档全文，请拆解功能点：\n\n${doc}`);
  const points = extractJson<FunctionalPoint[]>(raw);
  if (!Array.isArray(points) || points.length === 0) {
    throw new Error("需求解析失败：未得到有效的功能点数组");
  }
  console.log(`✅ 解析出 ${points.length} 个功能点`);
  return points;
}

/** 阶段二：评审 → 通过与否 */
export async function reviewRequirements(points: FunctionalPoint[]): Promise<ReviewResult> {
  const raw = await runStage(reviewerAgent,
    `请评审以下功能点清单：\n${JSON.stringify(points, null, 2)}`);
  const result = extractJson<ReviewResult>(raw);
  if (!result.passed) {
    // 不通过就终止流水线，把问题抛给上层处理
    throw new Error(`❌ 需求评审未通过：${result.blocker}\n风险：${result.risks.join("；")}`);
  }
  console.log(`✅ 评审通过，关注 ${result.risks.length} 个风险点`);
  return result;
}
```

::: warning 每个 Agent 都是有状态的
四个 Agent 各自维护独立的 `messages` 历史。如果同一批需求要复跑，记得先 `agent.reset()`，否则上次的文档会残留在上下文里污染结果。
:::

## 19.5 阶段三：测试方案生成

```typescript
// pipeline/stage3.ts
import { runStage, extractJson } from "./run.js";
import type { FunctionalPoint, ReviewResult, TestPlan } from "./types.js";
import { plannerAgent } from "./agents.js";

export async function makeTestPlan(
  points: FunctionalPoint[],
  review: ReviewResult,
): Promise<TestPlan> {
  // 把上一阶段的两份结构化输出都作为输入——评审意见直接影响策略
  const raw = await runStage(plannerAgent,
    `功能点清单：\n${JSON.stringify(points)}\n\n` +
    `评审意见：\n${JSON.stringify(review)}\n\n请制定测试方案。`);
  const plan = extractJson<TestPlan>(raw);
  console.log(`✅ 方案完成：${plan.methods.join("、")}`);
  return plan;
}
```

注意 `focusAreas` 的用法：评审阶段发现「未定义并发上限」，方案的 focusAreas 就应包含「购物车并发操作」。这种**跨阶段信息流动**正是多 Agent 流水线优于单个大 prompt 的地方。

## 19.6 阶段四：参考交互稿设计图生成用例

这是本章的重头戏。UI 用例的质量取决于对界面元素的了解——把**交互稿设计图**作为图片输入喂给用例生成 Agent（第 12 章的多模态能力在这里落地）：

```typescript
// pipeline/stage4.ts —— 用例生成（支持设计图）
import { readFileSync } from "node:fs";
import { runStage, extractJson } from "./run.js";
import type { FunctionalPoint, ReviewResult, TestPlan, TestCase } from "./types.js";
import { caseGenAgent } from "./agents.js";

export async function generateCases(
  points: FunctionalPoint[],
  review: ReviewResult,
  plan: TestPlan,
  mockupPaths: string[] = [],          // 交互稿设计图路径列表
): Promise<TestCase[]> {
  // 1) 准备文本上下文
  const context =
    `功能点清单：\n${JSON.stringify(points)}\n\n` +
    `评审意见：\n${JSON.stringify(review)}\n\n` +
    `测试方案：\n${JSON.stringify(plan)}\n\n` +
    `附带 ${mockupPaths.length} 张交互稿设计图，` +
    `请对照图中页面元素与交互流程补充 UI 用例。`;

  // 2) 设计图读取为 base64 图片块（第 12 章的消息格式）
  const images = mockupPaths.map((p) => ({
    type: "image" as const,
    data: readFileSync(p).toString("base64"),
    mimeType: p.endsWith(".png") ? "image/png" : "image/jpeg",
  }));

  // 3) 文本 + 图片一起发给用例生成 Agent
  const raw = await runStage(caseGenAgent, context, images);
  const cases = extractJson<TestCase[]>(raw);

  // 4) 基本校验：编号唯一、必填字段齐全
  const ids = new Set<string>();
  for (const c of cases) {
    if (ids.has(c.id)) throw new Error(`用例编号重复：${c.id}`);
    ids.add(c.id);
    if (!c.steps?.length || !c.expected) {
      throw new Error(`用例 ${c.id} 缺少步骤或预期结果`);
    }
  }
  console.log(`✅ 共生成 ${cases.length} 条用例` +
    `（UI 类 ${cases.filter((c) => c.type !== "api").length} 条）`);
  return cases;
}
```

::: tip 设计图带来的差异
没有设计图时，UI 用例只能靠模型想象页面结构（容易漏元素）；提供交互稿后，模型会针对图中**实际存在的按钮、输入框、弹窗**逐一生成用例，甚至能发现「设计稿里这个按钮在禁用态没有视觉区分」这类可用性问题。
:::

## 19.7 主流程串联

```typescript
// pipeline/main.ts —— 完整流水线入口
import { parseRequirements, reviewRequirements } from "./stages1-2.js";
import { makeTestPlan } from "./stage3.js";
import { generateCases } from "./stage4.js";
import { writeFile } from "node:fs/promises";

async function main() {
  // 输入：需求文档 + 可选的交互稿设计图
  const mockups = process.argv.slice(3);   // node main.ts requirements.md a.png b.png

  const points = await parseRequirements(process.argv[2]);
  const review = await reviewRequirements(points);   // 不通过会抛错终止
  const plan = await makeTestPlan(points, review);
  const cases = await generateCases(points, review, plan, mockups);

  // 产物落盘，供第 20 章的自动化执行阶段消费
  await writeFile("cases.json", JSON.stringify(cases, null, 2));
  console.log(`📦 已输出 cases.json`);
}

main().catch((err) => {
  console.error(err.message);
  process.exit(1);
});
```

## 本章小结

- 四阶段各建一个专职 Agent：解析→评审→方案→用例，systemPrompt 单一职责；
- 阶段间用 `interface` 定义数据契约，JSON 输出经代码校验后再流转；
- 评审不通过即终止流水线并给出 blocker，杜绝带病测试；
- 用例生成阶段通过 `agent.prompt(text, images[])` 注入交互稿设计图，显著提升 UI 用例的元素覆盖率；
- 复跑前记得 `agent.reset()`，避免历史上下文污染。
