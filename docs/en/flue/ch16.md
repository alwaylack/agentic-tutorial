# Chapter 16 · Deployment: CI and Hosted Platforms

> Chapter goals: Learn to run agents in GitHub Actions / GitLab CI, use Daytona and Render as deployment targets, and consume deployed agent sessions with @flue/sdk.

## 16.1 Scenarios for Running Agents in CI

Agents in CI are not long-lived services — they "run one task and exit":

```text
① PR opened → agent reviews code and comments
② Scheduled task → agent patrols issues and labels them
③ Release pipeline → agent generates changelog
```

## 16.2 GitHub Actions

```yaml
# .github/workflows/agent-triage.yml
name: agent-triage
on:
  issues:
    types: [opened]        # Trigger on new issue
  schedule:
    - cron: "0 * * * *"   # Patrol hourly
jobs:
  triage:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npx flue run agents/triage.ts "${{ github.event.issue.title }}"
        env:
          # Keys from repo Settings → Secrets; never hardcode
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

```yaml
# Static validation before actual execution (good habit to save tokens)
      - name: dry-run validate agent definition
        run: npx flue run agents/triage.ts --dry-run
```

## 16.3 GitLab CI/CD

```yaml
# .gitlab-ci.yml — equivalent GitLab pipeline
agent-triage:
  image: node:22
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"   # Schedule trigger
  script:
    - npm ci
    # Keys from GitLab CI/CD Variables (masked)
    - npx flue run agents/triage.ts "$ISSUE_TITLE"
  variables:
    ANTHROPIC_API_KEY: $ANTHROPIC_API_KEY
```

::: tip CI running注意点
- Each job is a新环境: Durability state must use an external database for retry to接力;
- Jobs have time limits: split长 tasks into segments or use `--output` to persist中间结果;
- Logs are观测: enable verbose output in CI for easier debugging.
:::

## 16.4 Hosted Platforms: Daytona and Render

| Platform | Role | Key Points |
|---|---|---|
| Daytona | Remote sandbox | Provides isolated container execution environment for the agent |
| Render | Node service hosting | Long-lived process + env var injection + Postgres add-on |

## 16.5 @flue/sdk: Consuming Deployed Sessions

After deployment, the frontend or other services read agent sessions via the SDK:

```typescript
import { FlueClient } from '@flue/sdk';

const client = new FlueClient({
  baseUrl: 'https://your-flue-app.example.com',
});

// Send a message to a session
const result = await client.dispatch('triage', [
  { role: 'user', content: 'Triage issue #42' },
]);
console.log('Session ID:', result.id);

// Read session history
const session = await client.getSession(result.id);
console.log('Messages:', session.messages.length);
```

## 16.6 Chapter Summary

- CI scenarios: PR review, scheduled patrol, release changelog — all "run once and exit";
- GitHub Actions / GitLab CI: inject keys via secrets/variables; use `--dry-run` for static validation;
- Daytona: remote sandbox provider for isolated execution;
- Render: Node service hosting with Postgres add-on for persistence;
- @flue/sdk: consume deployed agent sessions from any client.
