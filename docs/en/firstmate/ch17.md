## 17.3 Dispatch Profiles: Choosing Different Harnesses per Task

By default, all crewmates use the same crewmate harness (`config/crew-harness`). When不同任务的性质差异很大, you can启用 **dispatch profiles**: an optional local gitignored file `config/crew-dispatch.json`, written in **natural language rules** that the firstmate reads before dispatching and uses its judgment to match.

```json
{
  "rules": [
    {
      "when": "bug fix or a ship task needing the full test pipeline",
      "use": [{ "harness": "claude", "effort": "high" }],
      "why": "Fix tasks need strong tool calling and long context"
    },
    {
      "when": "architecture audit, code research scout tasks",
      "use": [
        { "harness": "pi", "model": "deepseek-chat" },
        { "harness": "grok" }
      ],
      "why": "Research prioritizes低成本高吞吐; array form做配额感知的备选"
    }
  ],
  "default": [{ "harness": "claude" }]
}
```

Official schema要点:

- Each rule必须有 `when` and `use`; `use` and the top-level `default` both accept a single profile object or a非空数组 (array undergoes quota-array-dispatch for配额感知 selection);
- `model`, `effort` (`low|medium|high|xhigh|max`), and rule-level `why` are all optional; omitting uses that harness's own default;
- The shell script does not parse semantics — **matching rules relies on the firstmate's judgment**; the script only负责 passing the selected `--harness/--model/--effort`具体参数 to `fm-spawn.sh` and validating JSON shape (bootstrap uses `jq` validation;非法配置 reports `CREW_DISPATCH: invalid ...` diagnosis rather than being silently bypassed).

Twobehavior changes to know: **once this file exists, `fm-spawn.sh` refuses any crewmate/scout launch without an explicit harness** (`config/crew-harness` no longer auto-fallback); secondmate launch is exempt from this constraint, still走 `config/secondmate-harness`. Also, this file is inherited into secondmate homes, letting the entire fleet共享 the same dispatch strategy.

```bash
# No restart needed after writing; auto-validates on next bootstrap
cat config/crew-dispatch.json | jq empty && echo "JSON OK"
```

## 17.4 Per-Project Merge Permissions: Three Modes in Place

From Chapter 10, each project's standing posture is recorded in `data/projects.md`. This chapter assigns the most suitable mode for each of the three projects:

| Project | Mode | Rationale |
|---|---|---|
| web-api | `direct-PR` | Bug fix希望尽快出 PR 走 CI 复核; no-mistakes full pipeline not needed |
| data-pipeline | (no ship) | Scout tasks never push; no merge issue |
| cli-tool | `local-only` | Small feature local quick-change; firstmate does a fast-forward local merge after your approval |

The one-sentence official semantics for the three modes: `no-mistakes` runs the full validation pipeline; `direct-PR` skips the pipeline and opens a PR directly; `local-only` stays local until the firstmate performs an approved fast-forward merge. The optional `+yolo` flag grants merge autonomy — this chapter刻意 does not use it, so every merge passes through your hand.

One safety detail: if a ship task's执行严格度 is below the project's registered posture, spawn prints a deviation notice and continues — the registration is not装饰, deviations are显式 exposed.
