# Chapter 18 · Capstone 3: Secondmate Remote Fleet Scaling Operations

> Chapter goals: Upgrade the personal fleet built in Chapter 16 to a scaled deployment — local secondmate + remote home + Relay应答 + /afk on-call mode — and complete a production-grade ops drill.

## 18.1 Capstone Blueprint and Preparation

In the first two capstones, you only指挥 a single fleet managed directly by the firstmate. This chapter introduces two scaling upgrades:

```text
Before (Capstone 1/2):
captain ──> firstmate ──> crewmate × N (one worktree per task)

After (this chapter):
captain ──> firstmate (primary home)
             ├──> secondmate A (local isolated FM_HOME)
             ├──> secondmate B (complete home on a remote host, Herdr fm-remote session)
             └──> crewmate × N
```

Recalling the official definition: **a secondmate is a crewmate with an isolated firstmate home and a charter, not a second architecture**. It has its own persistent `FM_HOME` — independent state, backlog, projects, and session lock; and **secondmates do not spawn secondmates**, so `config/secondmate-harness` only生效 on the primary and is never inherited.

Preparation for this chapter:

- A completed Capstone 2 fleet environment (tmux backend available, `gh auth login` completed);
- An SSH-reachable remote host (cloud server or another Mac/Linux at home);
- An X or Discord account (for Relay drill; can skip).

## 18.2 Step One: Provision a Local Secondmate

First write the charter for the secondmate, then启动. The charter is its brief (`kind=secondmate` in `data/<id>/brief.md`): telling this "deputy" what class of tasks it负责 and who it reports to.

Issue a natural-language指令 to the firstmate to complete provisioning, or启动 directly with the script:

```sh
# Execute in the firstmate primary home repo root:
# Have the firstmate建 the home and启动 for a secondmate with id "ops"
bin/fm-spawn.sh ops --secondmate
```

On launch, the primary解析 the secondmate专用 harness. Specified via the local gitignored file `config/secondmate-harness`, first line format: `<harness> [<model>] [<effort>]`:

```sh
# config/secondmate-harness —— fix the secondmate to use pi, model and effort optional
pi
```

Resolution rules to remember:

- When the file is absent or writes `default`, fallback to `config/crew-harness`, then to the primary's own harness;
- Explicitly passed `--harness` / `--model` / `--effort` to `fm-spawn.sh` override this file, but only for that one spawn;
- **This file is NOT inherited** — because secondmates do not spawn secondmates, this switch naturally stays only in the primary's hands.

## 18.4 Step Three: Migrate to a Remote Secondmate (Doctor → Seed → Spawn)

Now move a secondmate's entire home to a remote host. Three iron rules to remember first:

1. **What moves remote is the entire home**, not a single worker; the primary retains路由 and supervision权; the remote home has its own projects, backlog, and workers;
2. The remote secondmate agent **永远跑 in the Herdr backend's shared `fm-remote` session** — that service belongs to the remote host's own GUI login session, not the SSH connection, so断线 does not带走 the agent endpoint;
3. **An unavailable remote route is marked unknown only; it never降级 to a local replacement.**

### 3.1 Remote Host Pre-bury

Clone FirstMate on the remote host to an absolute path and expose the fixed entry to the non-interactive PATH:

```sh
# Execute on the remote host
mkdir -p ~/.local/bin
ln -s /absolute/path/to/firstmate/bin/fm-remote-entrypoint.sh \
      ~/.local/bin/fm-remote-entrypoint.sh
```

The entry accepts only encoded-argv form真实可执行的 `bin/fm-*.sh`; it never accepts shell command strings. Note: do not enable agent forwarding — `fm-on.sh` actively禁用 it on each call, and arms bounded SSH dead-peer detection, so a gone host fails within a有限 window rather than hanging无限.

### 3.2 Doctor → Seed → Spawn

```sh
# Phase 1: doctor — read-only readiness check (human缺口永不全自动修复)
bin/fm-remote-doctor.sh <ssh-alias>

# Phase 2: seed —播 the remote home (after doctor绿灯)
bin/fm-remote-home-seed.sh <id> <ssh-alias> <remote-root> <remote-home> \
    myapp=https://github.com/you/myapp.git

# Phase 3: spawn —启动 the secondmate on the remote
bin/fm-spawn.sh <id> --secondmate
```

## 18.5 Relay: Public Mention应答安全模型

Enable Relay with a local `.env` paired token:

```bash
# .env (gitignored)
RELAY_X_TOKEN=xxx
RELAY_RELAY_DISCORD_TOKEN=xxx
```

The安全模型核心: **Relay only responds to public mentions, never主动 DM or私聊**. The firstmate sees the mention, routes it through the normal intake契约, and replies in公开上下文 — never exposing internal state or crewmate工作细节.

Safety boundary: Relay上线先 dry-run — `would-be replies` are本地留痕,人工审阅后再放行,最多七天内三条公开跟进.

## 18.6 /afk + Wedge-Alarm:无人值守兜底

Configure `config/wedge-alarm` to push alerts to your phone:

```sh
# config/wedge-alarm
command: curl -X POST https://your-webhook.url -d '{"text":"WEDGE: $MESSAGE"}'
```

Then activate away mode:

```text
> /afk
```

During /afk: the bash sub-supervisor handles routine notifications零 token; batches captain-related events into digests; and the wedge-alarm triggers响亮 alerts when delivery wedges. The限频机制 ensures at most one alarm per max-defer window, with a default 10-second timeout.

## 18.7 次日回岗: /ahoy and /stow

Next day back at the desk, a single `/ahoy` gives you the event recap since the last real captain message, with unresolved items guided one-by-one in impact order; if `/ahoy` is the first real message of this session, it退化 to a Bearings summary.

Before closing the session, run:

```text
/stow
```

This内置技能清扫未捕获的持久知识, persisting known-unarchived or stale work records to disk;策展分层 startup memory with衰减与冷归档策略; enforcing each home's budget约束 (exceeding上报决策 rather than硬塞); cascading同步 to registered secondmates. The budget is the `config/startup-memory-budget` from Section 18.3, with a stable estimation formula of `ceil(UTF-8 bytes / 3)` per file — a conservative portability approximation, not any vendor's精确 tokenizer.

## 18.8 全家桶更新: /updatefirstmate

The final piece of scaled ops:

```text
/updatefirstmate
```

This skill performs a fast-forward-only origin pull update on the running firstmate and all its secondmates, then re-reads instructions and notifies secondmates. The fast-forward-only保证 the update never creates a历史分叉 — if it cannot pull, itstops and reports rather than强推.

## 18.10 Chapter Summary

- Secondmate = independent FM_HOME + charter crewmate: own state/backlog/projects/session lock; does not spawn secondmates, so `config/secondmate-harness` only生效 on primary;
- Remote migration three-step: `fm-remote-doctor.sh` readiness gate (human缺口永不全自动) → `fm-remote-home-seed.sh` seed → `fm-spawn.sh <id> --secondmate` launch, all in Herdr `fm-remote` sessions;
- Failure semantics must be precise: SSH exit 255 is "unknown" not "dead"; only correlation-preserving重发 is safe; unavailable remote routes投影为 unknown and never降级为本地替换;
- Relay上线先 dry-run: would-be replies locally留痕, human审阅后再放行, max三条公开跟进 in seven days;
- `/afk` + wedge-alarm form the无人值守兜底: bash sub-supervisor零 token handles routine events, wedge限频响亮 alerts; `/stow` and `/updatefirstmate` close the knowledge governance and version推进 loop.
