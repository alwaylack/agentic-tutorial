# Chapter 6 · Assertions and Failure Detection

> Chapter goals: master request-level assertions with `catch_response=True`; manually mark failures with `resp.failure()`; aggregate statistics via the `name=` parameter; build reliable success-condition judgment logic.

## 6.1 Why Assertions Are Needed

By default, Locust judges request success/failure solely by HTTP status code: 2xx is success, 4xx/5xx is failure. But in production, "returning 200 with error data" is very common—e.g., the API returns `{"code": 500, "msg": "Internal error", "data": null}` yet the HTTP status code is still 200.

Load testing without assertions is like a temperature check without a thermometer: you see all requests "succeeded," but the system may already have problems.

```python
from locust import HttpUser, task, between

class ApiUser(HttpUser):
    wait_time = between(1, 3)
    host = "https://api.example.com"

    @task
    def get_user(self):
        # Default behavior: only checks HTTP status code
        self.client.get("/api/users/1")
        # Status code 200 → marked as success (even if body is an error message)
```

## 6.2 catch_response=True

Pass `catch_response=True` to methods like `self.client.get()` / `post()`, and Locust pauses automatic marking, letting you manually decide whether this request counts as success or failure:

```python
from locust import HttpUser, task, between
import json

class ApiUser(HttpUser):
    wait_time = between(1, 2)
    host = "https://api.example.com"

    @task
    def get_user_with_assertion(self):
        with self.client.get("/api/users/1", catch_response=True) as resp:
            # Assertion 1: HTTP status code must be 200
            if resp.status_code != 200:
                resp.failure(f"Unexpected status: {resp.status_code}")
                return

            # Assertion 2: response body must be valid JSON
            try:
                data = resp.json()
            except json.JSONDecodeError:
                resp.failure("Response is not valid JSON")
                return

            # Assertion 3: business code must be 0
            if data.get("code") != 0:
                resp.failure(f"Business error: code={data.get('code')}, msg={data.get('msg')}")

            # Assertion 4: required field exists
            if "data" not in data or not data["data"]:
                resp.failure("data field missing or empty")
```

The `with ... as resp` syntax is Python's context manager. When entering the `with` block, Locust pauses statistics; when exiting, it marks success/failure based on whether you called `resp.failure()`.

::: tip success() method
You can also explicitly call `resp.success()` to mark success, but this is not required—if you don't call `failure()`, Locust auto-marks success when exiting the `with` block.
:::

## 6.3 Custom Statistic Names (name= parameter)

When URLs contain dynamic path parameters (e.g., `/api/users/12345`), each different ID generates a separate statistic record, causing statistics table explosion. Use the `name=` parameter to aggregate them:

```python
import random
from locust import HttpUser, task, between

class SearchUser(HttpUser):
    wait_time = between(1, 3)
    host = "https://api.example.com"

    @task
    def search_products(self):
        for i in range(100):
            self.client.get(
                f"/api/products/{random.randint(1, 1000)}",
                name="/api/products/[id]",  # aggregate under one name
            )
```

## 6.4 Response Time Assertions

You can also use response time as an assertion condition:

```python
from locust import HttpUser, task, between

class ApiUser(HttpUser):
    wait_time = between(1, 2)
    host = "https://api.example.com"

    @task
    def fast_response(self):
        with self.client.get("/api/data", catch_response=True) as resp:
            if resp.response_time > 500:  # 500ms threshold
                resp.failure(f"Response too slow: {resp.response_time}ms")
            else:
                resp.success()
```

## 6.5 Global Success Conditions

Sometimes you need to judge overall pass/fail after the entire load test ends. Achieve this with event hooks:

```python
from locust import events
import logging

# Collect global error rate
stats = {"total": 0, "failures": 0}

@events.request.add_listener
def on_request(request_type, name, response_time, response_length, exception, **kwargs):
    stats["total"] += 1
    if exception:
        stats["failures"] += 1

@events.quitting.add_listener
def on_quitting(environment, **kwargs):
    """Check global success rate when load test ends"""
    if stats["total"] > 0:
        error_rate = stats["failures"] / stats["total"]
        if error_rate > 0.05:
            logging.error(f"Load test FAILED! Global error rate {error_rate:.1%} exceeds 5% threshold")
            environment.process_exit_code = 1
        else:
            logging.info(f"Load test PASSED, error rate {error_rate:.1%}")
```

After setting `environment.process_exit_code = 1`, CI/CD pipelines can judge whether the load test met requirements via the exit code.

## Chapter Summary

- By default, success/failure is judged by HTTP status code; `catch_response=True` enables manual assertion mode;
- `resp.failure(msg)` marks failure, `resp.success()` explicitly marks success;
- `name=` aggregates dynamic path parameters, avoiding statistics table explosion;
- Response time can also serve as an assertion condition;
- Combine `events.quitting` hook with process exit code for CI/CD auto-judgment.
