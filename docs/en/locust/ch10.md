# Chapter 10 · Distributed Load Testing

> Chapter goals: master Locust's master/worker distributed architecture, and learn to launch large-scale concurrent pressure across multiple machines.

## 10.1 Why Distribution Is Needed

A single machine has limited CPU, memory, and network bandwidth. When you need to simulate tens of thousands or even hundreds of thousands of virtual users, a single-process Locust cannot provide sufficient throughput. Locust's distributed mode solves this through **one master node + multiple worker nodes**:

```text
┌──────────┐     ┌──────────┐
│  Master  │────▶│ Worker 1 │──▶ Target System
│ (Stats)  │     └──────────┘
│          │     ┌──────────┐
│          │────▶│ Worker 2 │──▶ Target System
└──────────┘     └──────────┘
```

The Master produces no requests — it only distributes user counts and task definitions to workers, and aggregates all workers' statistics. Each worker is an independent Python process running the same locustfile.

## 10.2 Starting the Master

```bash
locust -f locustfile.py --master --host https://api.example.com
# Default listens on port 8089 (Web UI)
# Worker communication ports are 5557 (TCP) and 5558 (UDP)
```

Key parameters:

| Parameter | Description |
|---|---|
| `--master` | Start in master mode |
| `--master-bind-host` | Bind address (default `*`) |
| `--master-bind-port` | Communication port (default 5557) |
| `--expect-workers` | Wait for specified number of workers to be ready before starting |

Using `--expect-workers` prevents the master from starting the test before all workers connect:

```bash
locust -f locustfile.py --master --expect-workers 4
```

## 10.3 Starting Workers

Execute on each load test machine:

```bash
locust -f locustfile.py --worker --master-host=192.168.1.100
# --worker declares this node as a worker
# --master-host points to the master's IP (default localhost)
```

::: tip Same locustfile
All workers must have access to the same version of locustfile.py as the master. Recommended approaches:
- Place locustfile in a shared filesystem or git repository;
- Or use Docker images for unified distribution.
:::

## 10.4 Capacity Planning

The number of concurrent users each worker can simulate depends on hardware and script complexity. Rule of thumb:

- **Simple HTTP GET**: ~2000–5000 concurrent users per worker;
- **Complex POST + JSON parsing**: ~500–1500 concurrent users;
- **CPU-intensive assertions or encryption**: Even lower.

Estimate the required number of workers:

```python
workers_needed = target_users / per_worker_capacity

# Example: target 50,000 users, each worker handles 2,500
workers_needed = 50_000 / 2_500  # = 20 worker machines
```

## 10.5 Docker Compose Orchestration

```yaml
version: "3"
services:
  master:
    image: locustio/locust
    ports: ["8089:8089"]
    volumes: [./locustfile.py:/mnt/locust/locustfile.py]
    command: -f /mnt/locust/locustfile.py --master

  worker:
    image: locustio/locust
    volumes: [./locustfile.py:/mnt/locust/locustfile.py]
    command: -f /mnt/locust/locustfile.py --worker --master-host master
    deploy:
      replicas: 5
```

```bash
docker compose up --scale worker=10
```

## Chapter Summary

- Master only does scheduling and statistics aggregation, does not produce requests; Workers are the actual pressure-generating nodes;
- All workers需 access the same locustfile; `--expect-workers` prevents premature startup;
- Per-worker concurrent capacity depends on script complexity and需 empirical calibration.
