# Chapter 10 · Distributed Load Testing

> Chapter goals: master Locust's master/worker distributed architecture; learn to launch large-scale concurrent pressure across multiple machines.

## 10.1 Why Distributed Testing Is Needed

A single machine has limited CPU, memory, and network bandwidth. When simulating tens or hundreds of thousands of virtual users, a single-process Locust cannot provide sufficient throughput. Locust's distributed mode solves this with **one master node + multiple worker nodes**:

```text
┌──────────┐     ┌──────────┐
│  Master  │────▶│ Worker 1 │──▶ Target System
│(Stats)   │     └──────────┘
│          │     ┌──────────┐
│          │────▶│ Worker 2 │──▶ Target System
└──────────┘     └──────────┘
```

The Master produces no requests—it only distributes user counts and task definitions to workers, and aggregates statistics from all workers. Each worker is an independent Python process running the same locustfile.

## 10.2 Starting the Master

```bash
locust -f locustfile.py --master --host https://api.example.com
# Defaults to listening on port 8089 (Web UI)
# Worker communication ports: 5557 (TCP) and 5558 (UDP)
```

Key parameters:

| Parameter | Description |
|---|---|
| `--master` | Start in master mode |
| `--master-bind-host` | Bind address (default `*`) |
| `--master-bind-port` | Communication port (default 5557) |
| `--expect-workers` | Wait for specified number of workers before starting |

Use `--expect-workers` to prevent the master from starting the test before all workers connect:

```bash
locust -f locustfile.py --master --expect-workers 4
```

## 10.3 Starting Workers

Execute on each load-testing machine:

```bash
locust -f locustfile.py --worker --master-host=192.168.1.100
# --worker declares this node as a worker
# --master-host points to the master's IP (default localhost)
```

::: tip Same locustfile
All workers must access the same version of locustfile.py as the master. Recommended approach:
- Store locustfile in a shared filesystem or git repository;
- Or use Docker images for uniform distribution.
:::

## 10.4 Capacity Planning

The concurrent user count each worker can simulate depends on hardware and script complexity. Rule of thumb:

- **Simple HTTP GET**: ~2,000–5,000 concurrent users per worker;
- **Complex POST + JSON parsing**: ~500–1,500 concurrent users per worker;
- **CPU-intensive assertions or encryption**: even lower.

Estimate required worker count:

```python
workers_needed = target_users / per_worker_capacity

# Example: target 50,000 users, 2,500 per worker
workers_needed = 50_000 / 2_500  # = 20 workers
```

## 10.5 Docker Compose Orchestration

```yaml
version: "3"
services:
  master:
    image: locustio/locust
    ports: ["8089:8089"]
    volumes: [./locustfile.py:/mnt/locust/locustfile.py]
    command: -f /mnt/locust/locustfile.py --master

  worker:
    image: locustio/locust
    volumes: [./locustfile.py:/mnt/locust/locustfile.py]
    command: -f /mnt/locust/locustfile.py --worker --master-host master
    deploy:
      replicas: 5
```

```bash
docker compose up --scale worker=10
```

## Chapter Summary

- Master only handles scheduling and statistics aggregation, does not generate requests; Workers are the actual pressure-generating nodes;
- All workers must access the same locustfile; `--expect-workers` prevents premature startup;
- Per-worker concurrency capacity depends on script complexity—needs empirical calibration.
