# Chapter 4 · Task Weights and Wait Time

> Chapter goals: precisely control virtual user behavior distribution — use @task weights and tasks lists to control task selection probability, and use between/constant/constant_pacing three strategies to control execution rhythm.

## 4.1 Two Ways to Write Task Weights

### Decorator Approach

```python
from locust import HttpUser, task


class MallUser(HttpUser):
    host = "https://httpbin.org"

    @task(1)
    def view_homepage(self):
        self.client.get("/")

    @task(3)  # Selection probability is 3x the above
    def search_product(self):
        self.client.get("/get?q=phone")

    @task(2)
    def add_to_cart(self):
        self.client.post("/post", json={"item": "phone", "qty": 1})
```

Total weight = 1+3+2 = 6, each task selection probability: Homepage 16.7%, Search 50%, Cart 33.3%.

### tasks List Approach

```python
class WeightedUser(HttpUser):
    host = "https://httpbin.org"
    tasks = {view_homepage: 1, search_product: 3}  # Dict {method: weight}
```

You can also use a list to represent repetition counts (equivalent to weight):

```python
tasks = [search_product] * 3 + [view_homepage]
```

Both approaches produce the same effect; decorators are more intuitive, dictionaries suit dynamic scenarios.

## 4.2 Three Wait Time Strategies

`wait_time` determines the pause between tasks, directly deciding the RPS calculation model:

```python
from locust import HttpUser, task, between, constant, constant_pacing


class WaitStrategies(HttpUser):
    host = "https://httpbin.org"

    # Strategy 1: Random interval (most common)
    wait_time = between(1, 5)

    @task
    def demo(self):
        self.client.get("/get")
```

| Strategy | Syntax | Behavior |
|---|---|---|
| `between(a, b)` | Randomly wait a~b seconds each time | Closest to real human behavior |
| `constant(t)` | Fixed wait t seconds | Simple and controllable |
| `constant_pacing(t)` | Task runs once per t seconds (including execution time) | **Precise control of iteration rate** |

### Difference between constant and constant_pacing

This is the most easily confused pair:

```python
# constant(3): after task execution, fixed additional wait of 3 seconds
# If task takes 2s, actual cycle = 2 + 3 = 5s
wait_time = constant(3)

# constant_pacing(3): guarantee one new iteration starts every 3 seconds
# If task takes 2s, only extra wait 1s; if task takes 4s, no wait, start next round immediately
wait_time = constant_pacing(3)
```

::: tip When to use constant_pacing
Choose it when you need an **exact RPS target**. For example, target RPS=100 with 50 concurrent users, then each user's pacing should be set to 50÷100 = 0.5 seconds. constant_pacing automatically compensates for task execution time fluctuations.
:::

## 4.3 SequentialTaskSet: Orderly Task Groups

By default, tasks are selected randomly. If you need to execute a group of operations in order (such as a complete checkout flow), use `SequentialTaskSet`:

```python
from locust import HttpUser, SequentialTaskSet, task


class CheckoutFlow(SequentialTaskSet):
    """Simulate complete shopping flow: browse → add to cart → checkout"""

    @task
    def browse(self):
        self.client.get("/get")

    @task
    def add_cart(self):
        self.client.post("/post", json={"action": "add_to_cart"})

    @task
    def pay(self):
        self.client.post("/post", json={"action": "pay"})


class ShoppingUser(HttpUser):
    host = "https://httpbin.org"
    tasks = {CheckoutFlow: 1}
    wait_time = between(2, 5)
```

Tasks inside `SequentialTaskSet` execute in declaration order. After completing one round, it restarts from the beginning. It can itself be assigned weights and mixed with other TaskSets or regular tasks.

## 4.4 Organization Best Practices

Real project load test scripts often contain dozens of interfaces. The recommended directory structure:

```text
loadtests/
├── locustfile.py          # Entry: User definition + TaskSet composition
├── flows/
│   ├── browse.py          # Browsing flow
│   ├── checkout.py        # Checkout flow
│   └── admin.py           # Admin operations
└── config/
    └── users.py           # Test account pool
```

Core principles:

- Encapsulate one "business flow" as a `TaskSet` or `SequentialTaskSet`;
- The User class is only responsible for composing these flows and assigning weights;
- Common logic (login, cleanup) goes in base classes or Mixins for reuse.

## Chapter Summary

- `@task(N)` and `tasks = {method: weight}` two ways to control task probability;
- `between` random pause most like real humans; `constant_pacing` can compensate for execution time fluctuations, suitable for precise RPS scenarios;
- `SequentialTaskSet` forces sequential execution, used for business flows that cannot be out of order (e.g., add to cart before checkout);
- For complex projects, split files by business flow, with the User class doing only composition.
