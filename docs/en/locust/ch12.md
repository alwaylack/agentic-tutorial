# Chapter 12 · Kubernetes Operator

> Chapter goals: use the Locust Kubernetes Operator to manage distributed load testing declaratively in a K8s cluster; master Helm installation, LocustTest CRD configuration, and monitoring integration.

## 12.1 Why an Operator Is Needed

The previous chapter used Docker Compose to orchestrate master + workers. But in a K8s environment, you want:

- **Declarative management** of load test configuration (YAML-as-code, Git-versionable);
- Automatic Pod restart on failure, automatic resource quota scheduling;
- Shared networking and monitoring with other services in the cluster.

The Locust Kubernetes Operator is a CRD + Controller that defines load testing as a K8s resource (`LocustTest`), automatically creating master/worker Jobs, mounting locustfiles, and exposing the Web UI.

## 12.2 Installing the Operator

### Method 1: Helm Chart (Recommended)

```bash
# Add the repository
helm repo add locust-operator https://locustio.github.io/k8s-operator
helm repo update

# Install to a dedicated namespace
helm install locust-operator locust-operator/locust-operator \
  --namespace locust-operator --create-namespace
```

Verify installation:

```bash
# Check operator pod status
kubectl get pods -A -l app.kubernetes.io/name=locust-operator
# Example output:
# NAMESPACE         NAME                                    READY   STATUS    AGE
# locust-operator   locust-operator-xxxxxxxxx-xxxxx         1/1     Running   18s

# Check CRD registration
kubectl get crd
# NAME                    CREATED AT
# locusttests.locust.io   2024-01-15T08:30:00Z
```

### Method 2: Manifest File

```bash
kubectl apply -f https://raw.githubusercontent.com/locustio/k8s-operator/main/dist/install.yaml
```

## 12.3 Creating Your First LocustTest Resource

```yaml
# locust-test.yaml
apiVersion: locust.io/v1
kind: LocustTest
metadata:
  name: my-load-test
spec:
  master:
    configMapName: "my-locustfile"       # reference to ConfigMap containing locustfile
    image: "locustio/locust:latest"
    replicas: 1
  worker:
    configMapName: "my-locustfile"
    image: "locustio/locust:latest"
    replicas: 5                          # 5 worker pods
  experiment_target: "http://my-app.default.svc.cluster.local:8000"
```

First create the ConfigMap to store the locustfile:

```bash
kubectl create configmap my-locustfile --from-file=locustfile.py
```

Then apply the load test resource:

```bash
kubectl apply -f locust-test.yaml
```

## 12.4 Inline Locustfile

For quick experiments, you can inline the locustfile directly in the YAML:

```yaml
spec:
  master:
    locustfile: |
      from locust import HttpUser, task
      class QuickUser(HttpUser):
          host = "http://my-app:8000"
          @task
          def hello(self):
              self.client.get("/hello")
  worker:
    replicas: 3
```

::: tip When to Use Inline
Inline is suitable for quick validation and small scripts; formal projects should use ConfigMap or Git repository references for version management.
:::

## 12.5 Monitoring and Cleanup

Access the Web UI (via port-forward):

```bash
kubectl port-forward svc/my-load-test-master 8089:8089
```

Open `http://localhost:8089` to see real-time charts.

Delete the load test resource (auto-cleans all Pods):

```bash
kubectl delete locusttest my-load-test
```

Uninstall the Operator:

```bash
helm uninstall locust-operator -n locust-operator
```

## Chapter Summary

- The Operator turns load testing into a K8s-native resource via CRD `locusttests.locust.io`;
- One-line Helm install: `helm install locust-operator locust-operator/locust-operator`;
- LocustTest YAML declares master/worker replica counts and locustfile source;
- Supports both ConfigMap reference and inline YAML modes;
- Deleting the CR auto-cleans all associated Pods.
