# Chapter 15 · Parallel Execution and Sharding

> Chapter goals: parallelize E2E suites with pytest-xdist, understand that "isolation is the prerequisite for parallelism," and master sharding and report merging in CI.

## 15.1 Why E2E Particularly Needs Parallelism

Each Playwright test case launches a browser context; serial single-process runs burn half an hour easily on 200 cases. The official parallel solution is pytest-xdist, with recommended process count at **half the logical CPU cores**:

```bash
pip install pytest-xdist
pytest --numprocesses 4        # official parallel switch
pytest -n auto                 # xdist shorthand: auto-allocate by CPU count
```

Each worker is an independent process with its own Playwright driver and browser instance — this is both the source of speed and the root of all pitfalls: **any mutable state shared across cases becomes flaky failures under parallelism**.

## 15.2 Isolation Is the Prerequisite for Parallelism

pytest-playwright creates fresh `context + page` for each test by default (browser instances reused per scope), so **the browser layer is naturally isolated**; real conflicts come from the system under test:

| Conflict Source | Symptom | Solution |
|---|---|---|
| Same account logged in concurrently | Sessions kick each other, cart data cross-contamination | Each worker uses independent test accounts (see fixture below) |
| Shared database records | Case A deletes data B is validating | Cases create and delete their own data (API data fabrication, see Chapter 17), or shard by worker/schema |
| Fixed ports / fixed file paths | Address already in use | Randomize ports, write temp files with tmp_path |
| Global counters / leaderboard assertions | Asserting "first place" while other workers write | Change assertions to relative (records you created are visible to you), avoid global state |

Worker-dimension isolated accounts inject like this:

```python
# conftest.py —— each xdist worker gets a different account
import pytest

WORKER_ACCOUNTS = ["user0@t.io", "user1@t.io", "user2@t.io", "user3@t.io"]


@pytest.fixture(scope="session")
def worker_account(worker_id: str) -> str:
    # worker_id is "master" (serial) or gw0/gw1/gw2...
    idx = 0 if worker_id == "master" else int(worker_id[2:])
    return WORKER_ACCOUNTS[idx % len(WORKER_ACCOUNTS)]
```

## 15.3 Distribution Granularity and Order Pitfalls

xdist defaults to distributing collected tests to workers **by case**, meaning two things must be top-of-mind:

- **Execution order cannot be depended on**. If cases have sequential dependencies (B's data is created by A), parallelism guarantees random failures — the correct approach isn't tuning order but making each case self-sufficient;
- If you truly need "cases in the same group locked to one worker" (e.g., sharing an expensive login), use `--dist loadscope` (distribute by module/class grouping) or `loadgroup` (with `@pytest.mark.xdist_group`):

```python
@pytest.mark.xdist_group(name="checkout")   # same-group cases lock to one worker
class TestCheckoutFlow:
    def test_add_to_cart(self, page): ...
    def test_pay(self, page): ...
```

```bash
pytest -n 4 --dist loadgroup
```

Also note: `-s` output and `print` logs interleave across workers; for debugging add `-o log_cli=true` or directly inspect the failing case's trace (Chapter 11) — more efficient.

## 15.4 Sharding and Report Merging in CI

Single-machine parallelism has an upper limit; large suites in CI commonly use **multi-machine sharding**: each machine runs a subset, then merge results. Pure pytest ecosystem lacks a Node-version `--shard` built-in equivalent; common practice combines xdist's `--dist loadfile` with environment variables for shard selection:

```yaml
# .github/workflows/e2e.yml key snippet
strategy:
  matrix:
    shard: [1, 2, 3]
steps:
  - name: Run shard
    run: |
      pip install pytest pytest-playwright pytest-xdist pytest-md-report
      # Shard by test filename hash — simple, reliable static sharding
      python scripts/pick_shard.py --total 3 --index ${{ matrix.shard }} > files.txt
      pytest $(cat files.txt) --numprocesses 4 \
        --tracing=retain-on-failure
  - name: Upload traces
    if: ${{ !cancelled() }}
    uses: actions/upload-artifact@v5
    with:
      name: traces-shard-${{ matrix.shard }}
      path: test-results/
```

Key points:

- **Shard key must be stable** (by filename, not runtime order), ensuring reruns of the same shard cover the same content;
- Failure artifacts (traces/screenshots) **uploaded per-shard named**, merged for viewing;
- JUnit XML reports (`--junitxml=report-{shard}.xml`) can be aggregated at the CI layer to show total pass rate.

::: tip Rule of Thumb
Start with `-n auto` maxing out a single machine; introduce matrix sharding only when single-machine time exceeds 10 minutes, avoiding premature infrastructure complexity.
:::

## 15.5 Parallel Failure Localization Flow

Three-step localization for parallel failures:

1. **Reproduce singly**: `pytest tests/test_x.py::test_y` — run serially once; if it passes, it's almost certainly a shared-state conflict, not a functional bug;
2. **Isolate the culprit**: `-n 2 --dist loadfile` to narrow scope, or temporarily mark suspicious modules to the same `xdist_group` to observe recovery;
3. **Preserve evidence**: open `pytest --tracing=retain-on-failure` when reproducing locally, use trace viewer to compare request timings across two runs.

## 15.6 Chapter Summary

- `pytest --numprocesses N` (official) or `-n auto` enables parallelism; process count at half CPU cores;
- Browser contexts naturally isolated; conflicts almost always from shared accounts/data/ports — solve with worker-dimension accounts and create-self-delete-data;
- xdist distributes by case in random order; sequential dependencies must be eliminated; same-group cases bound with `loadscope/loadgroup`;
- CI sharding must use stable keys, upload artifacts per-shard, aggregate via JUnit reports.
