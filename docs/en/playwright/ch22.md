## 22.1 E2E Positioning: Few and Precise, Guarding Critical Paths

First calibrate the mindset: **E2E test unit cost is the highest of all test layers** (slow, brittle, hard to debug); its value lies in verifying "the user's critical journeys truly work," not pursuing coverage. A healthy pyramid roughly:

| Layer | Magnitude | Run Timing | Responsibility |
|---|---|---|---|
| Unit tests | Thousands | Every push | Logic correctness (see this site's pytest tutorial) |
| API/component tests | Hundreds | Every PR | Service contracts, page fragments |
| **E2E critical paths** | 20–50 cases | Every PR (smoke) + daily full | Login, ordering, payment — core journeys |

据此把 E2E 再分三级，用 pytest marker 管理：

```python
# Register markers in pytest.ini
[pytest]
markers =
    smoke: smoke set, must-run on PR (under ~5 minutes)
    critical: critical paths, must-run before merge
    full: full regression, daily scheduled
```

```python
import pytest

@pytest.mark.smoke
def test_login(page):
    ...

@pytest.mark.critical
def test_place_order_end_to_end(page, login_as):
    ...
```

```bash
pytest -m smoke            # PR pipeline
pytest -m "critical or smoke"   # merge pipeline
pytest -m full             # nightly full
```

## 22.2 Environment and Test Data Factories

The most common production E2E翻车点 is data. Three principles:

1. **Dedicated environment**: never run write operations against production; test environments must be rapidly resettable;
2. **Self-fabricated data**: each test creates the data it needs, cleans up at the end (or use one-time database snapshots);
3. **API data fabrication preferred over UI**: UI data fabrication is slow and brittle.

Recommended "API prep + UI verify" division of labor:

```python
import requests
import pytest

API = "https://api.staging.example.com"

@pytest.fixture
def product(api_token):
    """Create a product via API, delete after test — UI only verifies display"""
    resp = requests.post(
        f"{API}/products",
        json={"name": "Test Product-Do Not Touch", "price": 9.9},
        headers={"Authorization": f"Bearer {api_token}"},
        timeout=10,
    )
    product = resp.json()
    yield product
    requests.delete(f"{API}/products/{product['id']}",
                    headers={"Authorization": f"Bearer {api_token}"}, timeout=10)

def test_product_visible_in_storefront(page, product):
    page.goto(f"https://staging.example.com/products/{product['id']}")
    expect(page.get_by_role("heading", name=product["name"])).to_be_visible()
```

Paired with Chapter 9's `storage_state` reusing login state, Chapter 13's parameterization extending data dimensions, a stable data foundation搭出.

## 22.3 Reports: Making Results Readable and Traceable

`pytest-playwright` itself carries no HTML reporter; production environments通常叠加一层报告插件:

```bash
pip install pytest-html          # lightweight solution
pytest --html=report.html --self-contained-html
```

For automatic screenshot embedding on failure, combine `--screenshot only-on-failure` with conftest hooks to挂图片 into the report. For more complete "historical trends + attachments + steps"需求, choose **Allure**:

```python
# pip install allure-pytest
import allure

@allure.feature("Shopping Cart")
@allure.story("Add Product")
def test_add_to_cart(page, product):
    with allure.step("Open product detail page"):
        page.goto(f"https://staging.example.com/products/{product['id']}")
    with allure.step("Add to cart and verify badge"):
        page.get_by_role("button", name="Add to Cart").click()
        expect(page.get_by_test_id("cart-badge")).to_have_text("1")
```

Whatever you选, three failure artifacts must保留 in CI: **trace.zip, screenshots, video** (Chapter 11's `--tracing retain-on-failure` etc. CLI args) — they're the唯一 basis for remote debugging.

## 22.4 Failure Classification and Alerting

Don't let all failures发出同一种噪音. Categorize by handling path:

- **Class A · Product Bug**: real defect → file a ticket to fix, this is testing's value所在;
- **Class B · Environment Issue**: service down, certificate expired → alert ops, mark test for retry;
- **Class C · Test Itself Flaky**: govern per Chapter 19 workflow;
- **Class D · Expected Change**: product intentionally changed causing assertion staleness → update the test and explain in the PR.

Alert design: `smoke` set PR failures directly block merges; nightly full failures reported at the next morning's standup,附报告链接与失败分类标签. Goal: **every red has an owner**.

## 22.5 Maintenance Checklist and Launch Checklist

**Monthly maintenance checklist:**

- [ ] Is the retry rate exceeding thresholds (>1% needs targeted governance)?
- [ ] Are there cases running longer than 60 seconds? Consider splitting or sinking to the API layer;
- [ ] Is the Playwright/browser内核版本落后超过一个大版本?
- [ ] Are storage_state, fixture account permissions still valid?

**Pre-launch E2E checklist:**

- [ ] New critical paths have corresponding `critical` cases;
- [ ] New page elements使用稳定的 `data-testid` (frontend联调约定);
- [ ] Real-time features involving WS/polling have message-layer assertions (Chapter 21);
- [ ] Accessibility structure assertions已更新 (Chapter 20);
- [ ] Test data可一键构造与清理 via API.

## 22.6 Chapter Summary

- E2E few and precise: smoke/critical/full three-tier markers,绑定分别 PR, merge, nightly pipelines;
- Data three principles: dedicated environment, self-create self-clean, API data fabrication UI verify;
- Report选型: `pytest-html`轻量起步, Allure要步骤与趋势; trace/screenshots/video are必备失败工件;
- Failure four-classification (Bug/环境/Flaky/预期变更), every red must have an owner;
- Use monthly maintenance checklists and launch checklists to keep the system持续健康.
