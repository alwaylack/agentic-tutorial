# Chapter 19 · Debugging Techniques and Flaky Testing Governance

> Chapter goals: master Playwright's official debugging toolchain (Inspector, headed mode, Trace Viewer), establish flaky test root-cause analysis workflows, making the test suite trustworthy again.

## 19.1 Why E2E Tests "Randomly Fail"

Flaky tests **run the same code, same command, sometimes pass sometimes fail**. They are E2E testing's greatest enemy: once a team gets used to "rerun when red," the entire test suite loses credibility. Common root causes categorize into four:

| Root Cause Category | Typical Symptom | Solution Direction |
|---|---|---|
| Animations/transitions | Element "invisible" or position offset | Wait for animation to end, or disable CSS animations |
| Network race conditions | Data not rendered at assertion time | Use Web-First assertions auto-retry (Chapter 5) |
| Time dependencies | Cases failing only at midnight/month-end | Inject fixed clock, forbid real-time dependency |
| Shared data | Fails under parallelism, passes serially | Test data isolation (Chapters 6/13) |

::: warning First Principle
The first reaction to encountering flaky shouldn't be "add retries" — **locate the root cause first**. Retries are just painkillers — they reduce failure probability, but the root cause remains, and one day it will explode in a more hidden way.
:::

## 19.2 PWDEBUG and Inspector: Official Debug Entry

Playwright's officially recommended debugging method is setting the environment variable `PWDEBUG=1`. It opens a three-piece combo at once:

1. **Inspector window**: visual step-by-step test execution;
2. **Headed browser** (headed mode): see real page changes;
3. **Timeout set to zero**: all auto-waits no longer timeout, convenient for careful observation.

```bash
# macOS / Linux: debug mode run (with -s to see print output)
PWDEBUG=1 pytest -s test_login.py::test_login_success

# Windows PowerShell
$env:PWDEBUG=1; pytest -s test_login.py::test_login_success
```

Inspector toolbar supports **play / pause / step**: each action executed (click, fill) highlights both the corresponding code line and the target element on the page, you can watch frame-by-frame "what the test actually did."

## 19.3 page.pause(): Start Debugging from a Specific Breakpoint

If the test is long and step-by-step too slow, insert a hard breakpoint where you care:

```python
def test_checkout_flow(page):
    page.goto("https://shop.example.com/cart")
    page.get_by_role("button", name="Checkout").click()

    # Stop from here, previous steps run directly
    page.pause()

    page.get_by_label("Shipping Address").fill("1 XX Road, Chaoyang District, Beijing")
    page.get_by_role("button", name="Submit Order").click()
    expect(page.get_by_text("Order Created")).to_be_visible()
```

`page.pause()` only takes effect under `PWDEBUG=1` (ignored during normal runs), so safely left in code for temporary debugging. When Inspector pauses at breakpoint, two high-frequency features:

- **Pick Locator**: hover mouse over any page element, Playwright auto-generates an **elastic locator** preferring role/text/testid;
- **Live editing**: directly modify the expression in Inspector's locator input box, matching element highlights in real-time — tune then copy back to code.

## 19.4 Trace Viewer: Best Post-Mortem Evidence

Inspector suits "debug on the spot," Trace suits "post-hoc investigation." Chapter 11 we configured `--tracing retain-on-failure`, now see how to use it to investigate an intermittent failure:

```bash
# Failed cases leave test-results/xxx.zip trace files
playwright show-trace test-results/test-cart-test-checkout-chromium.zip
```

Every page in Trace Viewer is an information dimension:

- **Actions**:耗时 and result for each action, red means failure point; hover shows before/after DOM snapshots;
- **Log**: action-level detailed logs (waiting for elements, scrolling, injected events...), see what Playwright repeatedly tried before timeout;
- **Network**: all requests and responses at that moment,一眼 identify "API didn't return" type races;
- **Console / Errors**: frontend JS errors often the real cause of test failures.

::: tip Investigation Routine
First look at Actions to find the failing action → switch to Log to see what it was waiting for → then Network/Console to find "who didn't arrive." 90% of flaky can be located along this chain.
:::

## 19.5 Waiting Strategy Correction: Don't Use sleep as a Crutch

Many teams' flaky tests were治出来的 by "patching with sleep":

```python
# ❌ Anti-pattern: however long you sleep, never safe, also slows the whole suite
time.sleep(3)
expect(page.get_by_text("Loading complete")).to_be_visible()
```

The correct approach returns to the two axes from Chapters 4 and 5:

```python
from playwright.sync_api import expect

# ✅ Action auto-waits: click waits until element visible, stable, event-receiving
page.get_by_role("tab", name="Order List").click()

# ✅ Web-First assertions built-in polling retry, until satisfied or timeout
expect(page.get_by_test_id("order-row")).to_have_count(10)
```

Two precise tools for special scenarios:

```python
# Wait for a specific network response before asserting (not wait fixed seconds)
with page.expect_response("**/api/orders") as resp_info:
    page.get_by_role("button", name="Refresh").click()
assert resp_info.value.ok

# When page has no "loading complete" marker, explicitly wait network idle
page.wait_for_load_state("networkidle")
```

## 19.6 Correct Retry Posture and Governance Workflow

In pytest ecosystem, add automatic retry to failed cases with `pytest-rerunfailures` plugin:

```bash
pip install pytest-rerunfailures
pytest --reruns 2 --reruns-delay 1   # global: at most rerun 2 times after failure
```

```python
import pytest

@pytest.mark.flaky(reruns=3, reruns_delay=2)
def test_known_flaky_until_bug_fixed(page):
    # Only locally retry for个别 known-issue cases, annotate with tracking issue number
    ...
```

But treat it as a **buffer-period management tool** not a solution, paired with a governance workflow:

1. **Record**: mark flaky cases with `@pytest.mark.flaky` and associate issue numbers;
2. **Quantify**: in CI reports stat retry rate, exceeding threshold (e.g., 1%) stop new features and fix it;
3. **Postmortem**: every case passing only after retry, follow 19.4's Trace flow once to find root cause;
4. **Eradicate**: remove flaky mark after root cause fixed — retry quota is a consumable, not a permanent exemption.

## 19.7 Chapter Summary

- Flaky four root causes: animations, network race, time dependency, shared data;
- `PWDEBUG=1 pytest -s` opens Inspector + headed + no-timeout debug combo;
- `page.pause()` is a hard breakpoint only effective in debug mode, paired with Pick Locator / Live editing for efficient locator tuning;
- `playwright show-trace` is first post-hoc evidence, investigation chain: Actions → Log → Network/Console;
- Replace `sleep` with `expect` auto-retry; `pytest-rerunfailures` only buffers, root causes must be eradicated.
