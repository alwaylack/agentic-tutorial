# Chapter 13 · Data-Driven and Parameterized E2E

> Chapter goals: use parametrize, fixture params, and external data sources to transform "same operations × multiple test datasets" into structured E2E cases, and learn to control parameter scale.

## 13.1 Why E2E Also Needs Data-Driven Testing

A login form has dozens of input combinations (empty password, malformed email, correct credentials...), and writing nearly identical test functions by hand is a maintenance disaster. The core idea of data-driven testing is: **separate "operation flow" from "test data"** — write the flow once, list the data in a table, and let the framework generate test cases in batch.

In E2E scenarios there are three common parameterization paths:

1. `@pytest.mark.parametrize`: run the same flow with multiple datasets;
2. **fixture params**: different environment/role dimensions (e.g., regular user vs administrator);
3. External data files (YAML/JSON): large datasets or when non-developers need to maintain them.

## 13.2 parametrize-Driven Form Validation

Take registration form validation as an example:

```python
# tests/test_signup_validation.py
import re
import pytest
from playwright.sync_api import Page, expect

# (email, password, expected message) triplets covering equivalent classes
INVALID_CASES = [
    ("", "Passw0rd!", "Please enter an email"),
    ("not-an-email", "Passw0rd!", "Invalid email format"),
    ("user@test.com", "", "Please enter a password"),
    ("user@test.com", "123", "Password must be at least 8 characters"),
]

@pytest.mark.parametrize("email,password,message", INVALID_CASES)
def test_signup_shows_validation(page: Page, email: str, password: str, message: str):
    page.goto("/signup")
    page.get_by_label("Email").fill(email)
    page.get_by_label("Password").fill(password)
    page.get_by_role("button", name="Sign Up").click()
    # Web-First assertion auto-waits for message to appear
    expect(page.get_by_role("alert")).to_contain_text(message)
```

One run generates 4 independent test cases, and any failure can pinpoint exactly which dataset caused it — something impossible when cramming all cases into a single function.

### Make Reports Readable with IDs

Default case names concatenate parameter values, and long strings look ugly. Customize naming with `ids`:

```python
@pytest.mark.parametrize(
    "email,password,message",
    INVALID_CASES,
    ids=["empty-email", "bad-format", "empty-password", "short-password"],
)
def test_signup_validation(page: Page, email, password, message):
    ...
```

You can also pass a function to generate dynamically: `ids=lambda val: f"case-{val}"` (called per parameter). Combined with `-k "empty-email"` you can filter runs by name.

## 13.3 Fixture Params for Multi-Role Scenarios

parametrize parameterizes "one dataset"; when the difference is **the entire environment identity** (accounts for different roles, different browser context configurations), fixture params are more suitable:

```python
# conftest.py
import pytest
from playwright.sync_api import Page

ROLES = {
    "admin":   {"user": "admin@shop.io",   "passwd": "Adm1n!Secret"},
    "buyer":   {"user": "buyer@shop.io",   "passwd": "Buyer!Secret"},
}

@pytest.fixture(params=list(ROLES), ids=["admin", "buyer"])
def logged_in_page(request, page: Page) -> Page:
    """Each role gets its own logged-in page"""
    cred = ROLES[request.param]
    page.goto("/login")
    page.get_by_label("Email").fill(cred["user"])
    page.get_by_label("Password").fill(cred["passwd"])
    page.get_by_role("button", name="Log In").click()
    expect(page.get_by_role("navigation")).to_contain_text(cred["user"])
    yield page
    page.context.close()  # ensure session isolation
```

```python
# tests/test_dashboard.py
def test_dashboard_visible(logged_in_page):
    """This test runs once for admin and once for buyer"""
    expect(logged_in_page.locator("#dashboard")).to_be_visible()
```

Each value in `params` instantiates the fixture once, and tests depending on it double — **expanding the role dimension requires no test code changes**.

## 13.4 External Data Sources: YAML for Complex Data

When data exceeds a dozen rows, placing it in Python files interferes with readability. Move it into YAML loaded uniformly by `conftest.py`:

```yaml
# data/products.yaml
- name: Mechanical Keyboard
  price: "399.00"
  stock: In Stock
- name: Monitor Stand
  price: "129.00"
  stock: Out of Stock
```

```python
# tests/test_search.py
import pathlib
import yaml
import pytest
from playwright.sync_api import Page, expect

DATA = yaml.safe_load(
    (pathlib.Path(__file__).parent.parent / "data" / "products.yaml").read_text("utf-8")
)

@pytest.mark.parametrize("item", DATA, ids=lambda i: i["name"])  # use product name as id
def test_product_card(page: Page, item: dict):
    page.goto(f"/search?q={item['name']}")
    card = page.locator(".product-card").first
    expect(card.get_by_class_name("price")).to_have_text(item["price"])
    # Stock badge text depends on data, not code
    expect(card.get_by_test_id("stock-badge")).to_contain_text(item["stock"])
```

JSON works similarly (`json.load`). The key point: **data files describe only facts, assertion logic stays singular**; adding a new product only requires changing YAML, not any test code.

## 13.5 Controlling Parameter Explosion: Equivalence Class Thinking

The biggest trap of parameterization is combinatorial explosion: 4 fields × 5 values per field = 625 E2E cases, each requiring a browser. Production practice:

- **Equivalence class partitioning**: pick boundary values + one typical value per form (empty / too long / invalid format / valid), no need to enumerate all;
- **Layered split**: push pure validation logic to unit/API layer tests (milliseconds), E2E keeps only representative paths that "can walk end-to-end" (API testing in Chapter 17 is precisely the承接点);
- **Orthogonal sampling**: use pairwise approach to manually pick dozens of representative combinations instead of full Cartesian product;
- **Reuse state on slow paths**: parameterized cases share the same `storage_state` (Chapter 9) to skip repeated login, compressing per-case time from minutes to seconds.

::: warning Decision Criterion
Before adding a parameter, ask: does it change the **behavior branch being verified**? If it's just swapping equivalent inputs, drop it.
:::

## 13.6 Chapter Summary

- parametrize manages "data", fixture params manage "environment/roles", complementary;
- `ids` makes case names readable and filterable in reports;
- YAML/JSON data files let non-developers maintain test data;
- Use equivalence classes and layered testing to control total E2E parameters, avoiding browser-level combinatorial explosion.
