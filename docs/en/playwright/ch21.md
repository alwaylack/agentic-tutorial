# Chapter 21 · WebSocket and Real-Time Application Testing

> Chapter goals: learn to listen and assert WebSocket traffic produced by pages, understand Playwright's WS mock capabilities and boundaries, and write stable automation tests for chat-room-like real-time features.

## 21.1 Testing Challenges of Real-Time Applications

Chat, collaborative docs, market data pushes, online customer service — this category's data is no longer driven by "request-response," but continuously pushed via WebSocket long connections. Traditional test approaches fail here:

- `expect_response` only waits for HTTP responses, can't catch server-initiated pushes;
- Pages may update at any moment, assertion timing hard to nail;
- Long connection lifecycles span multiple page events, improper close timing pollutes the next test.

Playwright's answer is two complementary APIs: **listening** (observe real traffic and assert) and **WebSocketRoute** (intercept/fake traffic).

## 21.2 Listening to WebSocket: page.on("websocket")

Each time the page establishes a WS connection, the `page.on("websocket")` event fires, callback receives a `WebSocket` object:

```python
def test_ws_connection_established(page):
    events = []
    # Record each time the page opens a new WebSocket connection
    page.on("websocket", lambda ws: events.append(ws.url))

    page.goto("https://chat.example.com/room/1")
    page.wait_for_timeout(1000)  # wait for connection (demo use, in prod use assertion waits)

    assert any(url.endswith("/ws/room/1") for url in events)
```

With the `WebSocket` object, continue listening to its frame events:

- `ws.on("framesent", handler)`: page **sent** a frame, callback param is `str | bytes`;
- `ws.on("framereceived", handler)`: page **received** a frame, callback param is `str | bytes`;
- `ws.on("socketerror", handler)`: connection error;
- `ws.on("close", handler)`: connection closed; `ws.is_closed()` queries state anytime.

## 21.3 Asserting Message Content: Collect + Wait Pattern

WS messages arrive asynchronously; the惯用 pattern is "**collect to a list, then poll with deadline assertion**" (note: Node.js's `expect(fn).toPass()` doesn't exist in Python — we implement equivalent semantics with a few lines of helper):

```python
import json
import time


def wait_until(predicate, timeout_ms=5000, interval_ms=100):
    """Poll until predicate true, timeout throws AssertionError (simulating Node's toPass semantics)"""
    deadline = time.monotonic() + timeout_ms / 1000
    while time.monotonic() < deadline:
        if predicate():
            return
        time.sleep(interval_ms / 1000)
    raise AssertionError(f"Condition not met within {timeout_ms}ms")


def test_receive_push_message(page):
    received = []

    def on_ws(ws):
        if ws.url.endswith("/ws/room/1"):
            # Parse each received frame and store in list
            ws.on("framereceived", lambda data: received.append(json.loads(data)))

    page.on("websocket", on_ws)
    page.goto("https://chat.example.com/room/1")

    # Server pushes online count every 2 seconds; poll-wait instead of fixed sleep
    wait_until(lambda: any(
        msg.get("type") == "presence" for msg in received
    ), timeout_ms=5000)
```

Sending-direction assertions likewise — verify the frontend indeed sent user input to the server:

```python
def test_client_sends_chat_message(page):
    sent = []

    def on_ws(ws):
        ws.on("framesent", lambda data: sent.append(data))

    page.on("websocket", on_ws)
    page.goto("https://chat.example.com/room/1")

    page.get_by_label("Message").fill("Hello everyone")
    page.get_by_role("button", name="Send").click()

    assert "Hello everyone" in sent  # framesent payload is the raw string/bytes
```

## 21.4 Mock WebSocket: WebSocketRoute

When the backend isn't ready yet, or you want to simulate exception scenarios (disconnects, error frames), intercept WS connections and fake server behavior. In Python sync API obtain `WebSocketRoute` via `page.route_websocket()`:

```python
def test_ui_renders_mock_push(page):
    def handle(ws):
        # Intercept connections to /ws/room/1, locally fake the server
        ws.on_message(lambda message: ws.send('{"type": "echo", "data": "%s"}' % message))

    page.route_websocket("**/ws/room/1", handle)
    page.goto("https://chat.example.com/room/1")

    page.get_by_label("Message").fill("hello")
    page.get_by_role("button", name="Send").click()

    # Page should render the mock server's echoed content
    expect(page.get_by_text("hello")).to_be_visible()
```

`WebSocketRoute`'s common capabilities:

- `ws.send(payload)`: **simulate server pushing** messages to the page;
- `ws.on_message(handler)`: observe/rewrite messages the page sends (handler return value replaces the original message);
- `ws.close()`: proactively simulate disconnect — test frontend reconnection and error-prompt logic.

::: warning Boundary Reminder
After mocking, traffic no longer reaches the real backend, so it validates **frontend WS protocol handling**, not end-to-end links. Protocol contracts themselves recommend covering with integration tests — the two shouldn't substitute each other.
:::

## 21.5 Comprehensive Case: Chat Room Full Send-Receive Chain

Combine listening and UI assertions, cover the complete "send → broadcast → render" loop:

```python
import json
import time
from playwright.sync_api import expect


def wait_until(predicate, timeout_ms=5000, interval_ms=100):
    deadline = time.monotonic() + timeout_ms / 1000
    while time.monotonic() < deadline:
        if predicate():
            return
        time.sleep(interval_ms / 1000)
    raise AssertionError(f"Condition not met within {timeout_ms}ms")


def test_chat_roundtrip(page):
    received = []

    def on_ws(ws):
        ws.on("framereceived", lambda d: received.append(json.loads(d)))
        ws.on("socketerror", lambda e: print("WS Error:", e))

    page.on("websocket", on_ws)
    page.goto("https://chat.example.com/room/1")

    # User sends a message
    page.get_by_label("Message").fill("Test message 001")
    page.get_by_role("button", name="Send").click()

    # UI shows own message (rendered after server broadcasts back)
    expect(
        page.locator(".chat-list").get_by_text("Test message 001")
    ).to_be_visible()

    # Protocol layer confirms the server indeed pushed back that message
    wait_until(lambda: any(
        m.get("type") == "chat" and m.get("text") == "Test message 001"
        for m in received
    ), timeout_ms=5000)
```

## 21.6 Long Connection Cleanup and Isolation

The easiest trap left by WS tests is **connection leaks**: the previous test's connection still open, the next test receives "ghost messages." Three commandments:

1. Each test uses an independent `BrowserContext` (pytest-playwright's `page` fixture does this by default), connections close with the context;
2. Proactively assert/wait for connections to close before test teardown, avoid race conditions:

```python
def test_connection_closes_cleanly(page):
    sockets = []
    page.on("websocket", lambda ws: sockets.append(ws))

    page.goto("https://chat.example.com/room/1")
    page.close()  # triggers frontend disconnect logic

    assert all(ws.is_closed() for ws in sockets)
```

3. Don't do heavy work in `framereceived` callbacks — callback blocking may slow the page event loop; collect data, assert in the main flow.

## 21.7 Chapter Summary

- `page.on("websocket")` captures connection establishment, `WebSocket` objects provide four event types: `framesent`/`framereceived`/`socketerror`/`close`, frame payloads are `str | bytes`;
- WS message assertions use "collect + poll-with-deadline" pattern, don't sleep;
- `page.route_websocket()` + `WebSocketRoute` can fake server pushes, rewrite messages, simulate disconnects, but only covers frontend logic;
- Long connection test three essentials: independent context, explicit close assertion, callbacks only collect don't process.
