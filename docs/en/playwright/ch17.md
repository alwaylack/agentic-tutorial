# Chapter 17 · APIRequestContext and API Testing

> Chapter goals: use Playwright's built-in APIRequestContext to test REST APIs directly, and combine "API data fabrication + UI verification" into the fastest test pattern.

## 17.1 Why Not Just Use requests

Playwright comes with a full HTTP client `APIRequestContext`, officially listed typical uses:

- Test server-side APIs directly;
- **Prepare server-side state via API before accessing the web app**;
- Validate server-side postconditions after browser operations.

Compared to requests/httpx, its unique advantage is **shared same-origin with browser context**: automatically carries cookies/auth state consistent with the page (Chapter 9's `storage_state` can be reused directly), and cleaned up uniformly when the context is destroyed — UI and API two channels naturally bridged.

## 17.2 Creating an Independent API Context

Official example pattern: session-scoped fixture + `playwright.request.new_context()`:

```python
# conftest.py
import os
from typing import Generator
import pytest
from playwright.sync_api import Playwright, APIRequestContext

API_TOKEN = os.getenv("GITHUB_API_TOKEN", "")


@pytest.fixture(scope="session")
def api_request_context(
    playwright: Playwright,
) -> Generator[APIRequestContext, None, None]:
    headers = {
        # Declare version per GitHub spec
        "Accept": "application/vnd.github.v3+json",
        "Authorization": f"token {API_TOKEN}",
    }
    request_context = playwright.request.new_context(
        base_url="https://api.github.com",
        extra_http_headers=headers,
    )
    yield request_context
    request_context.dispose()   # unified release
```

With `base_url`, all subsequent requests can use relative paths; `get/post/put/delete` methods return `APIResponse`, with common attributes `.ok` (2xx判定), `.status`, `.json()`, `.text()`.

## 17.3 Writing a Group of API Cases

Skeleton for official GitHub Issues example:

```python
# tests/test_issues_api.py
GITHUB_USER = "your-user"
GITHUB_REPO = "api-test-repo"


def test_should_create_bug_report(api_request_context: APIRequestContext):
    data = {"title": "[Bug] report 1", "body": "Bug description"}
    new_issue = api_request_context.post(
        f"/repos/{GITHUB_USER}/{GITHUB_REPO}/issues", data=data
    )
    assert new_issue.ok                       # assert 2xx

    issues = api_request_context.get(f"/repos/{GITHUB_USER}/{GITHUB_REPO}/issues")
    assert issues.ok
    issue = [i for i in issues.json() if i["title"] == "[Bug] report 1"][0]
    assert issue["body"] == "Bug description"
```

Paired with session-scoped setup/teardown managing the existence of "the resource under test" (create repo first, delete after run):

```python
@pytest.fixture(scope="session", autouse=True)
def create_test_repository(api_request_context: APIRequestContext):
    new_repo = api_request_context.post("/user/repos", data={"name": GITHUB_REPO})
    assert new_repo.ok
    yield                                     # ---- all tests run between here ----
    deleted = api_request_context.delete(f"/repos/{GITHUB_USER}/{GITHUB_REPO}")
    assert deleted.ok
```

### Schema Validation Thinking

After `.json()` gets a dict, besides asserting business fields, production recommends validating response structure (prevent silent field renaming). Python-side惯用 pydantic:

```python
from pydantic import BaseModel


class Issue(BaseModel):          # declare the field structure you depend on
    id: int
    title: str
    body: str | None


Issue.model_validate(new_issue.json())   # struct mismatch throws ValidationError
```

## 17.4 API Data Fabrication + UI Verification: Fastest Combo

The slowest part of E2E is walking the UI all the way to the target state. Hand "prep" to API, leave "verification" to UI:

```python
from playwright.sync_api import Page, expect


def test_last_created_issue_should_be_first_in_the_list(
    api_request_context: APIRequestContext, page: Page
):
    def create_issue(title: str) -> None:
        api_request_context.post(
            f"/repos/{GITHUB_USER}/{GITHUB_REPO}/issues",
            data={"title": title, "body": "Feature request"},
        )

    # Arrange: API seconds to fabricate three data points (UI might take dozens of seconds)
    create_issue("[Feature] request 1")
    create_issue("[Feature] request 2")

    # Act & Assert: only walk the browser for truly cared-about UI behavior
    page.goto(f"https://github.com/{GITHUB_USER}/{GITHUB_REPO}/issues")
    first = page.locator('[data-testid="issue-title"]').first
    expect(first).to_have_text("[Feature] request 2")
```

This official example demonstrates the golden layering: **state prep via API, user-perceptible behavior via UI**.

### Sharing Auth with Browser Context

For already-logged-in scenarios no need to reconfigure token — directly reuse login state saved in Chapter 9:

```python
request_context = playwright.request.new_context(
    base_url="https://shop.example.com/api",
    storage_state="state/auth.json",     # request context with cookies/token
)
resp = request_context.get("/orders")    # call as logged-in user
assert resp.ok
```

Conversely works too: requests issued from browser context accessible via `context.request` share the same cookie jar, suitable for post-operation immediate API verification.

::: warning data parameter
Python version `post(..., data=dict)` serializes dict as form/JSON; for explicit JSON also pass `data=json.dumps(payload)` and set `Content-Type` header. Refer to your version's API docs.
:::

## 17.5 Chapter Summary

- `playwright.request.new_context(base_url=..., extra_http_headers=...)` creates independent API client, `dispose()` cleanup;
- `APIResponse.ok/.status/.json()` cover常规断言需求, pydantic for schema validation;
- session fixture manages setup/teardown, tests manage single-behavior;
- **API data fabrication + UI verification** is E2E speedup's first lever; `storage_state` lets API and browser share login state.
