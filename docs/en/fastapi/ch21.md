# Chapter 21 · Configuration Management and Application Lifecycle

> Chapter goals: manage environment variable configurations with pydantic-settings; gracefully manage application-level resource startup and teardown with lifespan.

## 21.1 Why You Need Configuration Management

Values like database URLs, secrets, third-party credentials: they change per environment (dev/test/prod differ), and are often sensitive — shouldn't be written into the code repo. The industry standard practice is to put them in **environment variables**, read by the application at runtime.

But environment variables have a natural flaw — **they are always strings**:

```python
import os
items_per_user = os.getenv("ITEMS_PER_USER")   # "50" not 50
# Type conversion and validation must be handwritten; miss one spot and you get a production incident
```

## 21.2 pydantic-settings: Validated Configuration

`pydantic-settings` brings Pydantic's type conversion and validation capabilities to environment variables:

```bash
uv add pydantic-settings python-dotenv
```

```python
# config.py
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    app_name: str = "Awesome API"       # default values mean the env var is optional
    admin_email: str
    items_per_user: int = 50            # auto-converts from string to int and validates
    database_url: str = "sqlite:///./app.db"

    # Read from project-root .env file (requires python-dotenv)
    model_config = SettingsConfigDict(env_file=".env")


settings = Settings()  # reads environment variables on instantiation, case-insensitive
```

```bash
# .env (add to .gitignore!)
ADMIN_EMAIL="admin@example.com"
APP_NAME="ChimichangApp"
```

Instantiation resolves values by priority: **environment variables > .env file > default values**; environment variable names match field names case-insensitively (`APP_NAME` → `app_name`). Temporarily override at service startup:

```bash
ADMIN_EMAIL="deadpool@example.com" APP_NAME="ChimichangApp" fastapi run main.py
```

::: tip Keep configuration in an independent module
Put `Settings` in `config.py` (paired with the package structure from Chapter 19); everywhere uses `from .config import settings`. Note: `.env` must never be committed to Git.
:::

## 21.3 Settings as a Dependency + @lru_cache Singleton

The problem with using a global `settings` object directly: hard to replace in tests. A more elegant approach is to make configuration a dependency:

```python
# config.py —— note: no global instance created here this time
from functools import lru_cache
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    app_name: str = "Awesome API"
    admin_email: str
    items_per_user: int = 50

    model_config = SettingsConfigDict(env_file=".env")
```

```python
# main.py
from functools import lru_cache
from fastapi import Depends, FastAPI
from .config import Settings

app = FastAPI()


@lru_cache                # critical: only one Settings instance per process
def get_settings():
    return Settings()


@app.get("/info")
def info(settings: Settings = Depends(get_settings)):
    return {"app_name": settings.app_name}
```

Why do we need `@lru_cache`? If we only had `def get_settings(): return Settings()`, **every request would reinstantiate Settings and re-read the .env file from disk** — file IO is slow and completely unnecessary. With `@lru_cache`, the first call executes and caches the result; all subsequent requests reuse the same object.

And its biggest win as a dependency is **test-friendliness**:

```python
# test_main.py
def test_info_with_test_settings():
    def test_settings():
        return Settings(admin_email="test@example.com", _env_file=None)

    app.dependency_overrides[get_settings] = test_settings
    resp = client.get("/info")
    assert resp.json()["admin_email"] == "test@example.com"
    app.dependency_overrides.clear()
```

## 21.4 lifespan: Application Lifecycle Hooks

Some resources belong to the **entire application**, not individual requests: database connection pools, ML models, background task queues. They should be "created once at startup, released at shutdown." Modern FastAPI uses the `lifespan` parameter — an async context manager with `yield`:

```python
import contextlib
from fastapi import FastAPI, Request
from sqlalchemy.ext.asyncio import create_async_engine


@contextlib.asynccontextmanager
async def lifespan(app: FastAPI):
    # ===== Before yield: startup, executes once before the app starts accepting requests =====
    engine = create_async_engine(
        settings.database_url, pool_size=10, max_overflow=20,
    )
    app.state.engine = engine          # attach to app.state for use everywhere
    ml_models = {"model": load_expensive_model()}  # simulate loading a large model
    app.state.models = ml_models

    yield                               # ← the app handles all requests during this period

    # ===== After yield: shutdown, executes once after the app stops accepting requests =====
    await engine.dispose()             # release the connection pool
    del ml_models["model"]             # free VRAM/memory


app = FastAPI(lifespan=lifespan)


@app.get("/predict/{x}")
async def predict(x: float, request: Request):
    model = request.app.state.models["model"]  # each request reuses the same model
    return {"result": model.predict([x])}
```

Principle: `@asynccontextmanager` turns the function into an async context manager — executes the pre-yield half before entering the `with` block, the post-yield half on exit. FastAPI takes over this `with`: enters at startup, exits at shutdown.

::: warning Deprecated on_event
Old tutorials' `@app.on_event("startup")` / `@app.on_event("shutdown")` are **deprecated**. They are also mutually exclusive: once the `lifespan` parameter is passed, startup/shutdown event handlers are no longer invoked. New projects uniformly use `lifespan`.

Also distinguish: lifespan manages **application-level** resources (one per process); Chapter 11's `Depends(yield)` manages **request-level** resources (one per request).
:::

## 21.5 Chapter Summary

- Environment variables are always strings; pydantic-settings provides type conversion + validation + defaults + `.env` reading in one integrated solution;
- Resolution priority: real environment variables > `.env` > field defaults; `.env` must be added to `.gitignore`;
- Make configuration a dependency (`get_settings`) and use `@lru_cache` to guarantee exactly one instantiation and one disk read per process;
- Dependency-injected configuration can be swapped to test configs in seconds via `dependency_overrides`;
- Application-level resources use `FastAPI(lifespan=...)` + `@asynccontextmanager`: pre-yield is startup, post-yield is shutdown; `on_event` is deprecated.
