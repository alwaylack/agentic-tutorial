# Chapter 22 · Production Deployment Practice

> Chapter goals: understand the core conceptual model of production deployment; master multi-worker tuning, Docker image build best practices, health checks, and graceful shutdown.

## 22.1 The Conceptual Model of Deployment

When deploying FastAPI (or any web API), there are really only six things to care about:

1. **Security (HTTPS)** — handled by a TLS termination proxy **outside** the application;
2. **Auto-start on boot** — the application restarts automatically after server reboot;
3. **Crash restart** — the process recovers automatically if it crashes;
4. **Replication** — how many processes to run to leverage multiple cores;
5. **Memory** — control each process's memory usage;
6. **Pre-start steps** — database migrations, etc.

Understand a key分层: **the ASGI server (Uvicorn) runs your application, but HTTPS is typically not its job**. TLS termination proxies (Traefik / Caddy / Nginx + Certbot / cloud load balancers) decrypt traffic on the outer layer and forward HTTP to Uvicorn. And "keep-alive and restart" are handled by process managers like Docker/Kubernetes/systemd/Supervisor. Each has its own responsibility — don't ask Python processes to do the proxy's job.

```
Client --HTTPS--> TLS Termination Proxy (443) --HTTP--> Uvicorn/FastAPI (8000, internal network)
```

## 22.2 fastapi run and Multi-Worker Tuning

Use `fastapi dev` for development; the official CLI provides the production equivalent:

```bash
# Single process
fastapi run main.py --port 80

# Multi-worker: 1 parent + 4 worker subprocesses
fastapi run main.py --workers 4

# Equivalent native方式
uvicorn main:app --host 0.0.0.0 --port 8080 --workers 4

# If deployed behind Nginx/Traefik etc., trust proxy headers
fastapi run app/main.py --port 80 --proxy-headers
```

`--workers 4` launches 1 parent process (process manager) + 4 worker processes, each handling requests independently, leveraging multiple CPU cores.

Multi-worker quantity tuning heuristics:

- CPU-bound dominant → close to `CPU core count`;
- I/O-bound dominant (typical API app) → can go higher, e.g., `(2 × CPU) + 1`;
- Upper bound is memory-constrained: each worker is a full independent process, memory usage scales linearly;
- **Container/Kubernetes exception**: typically run **1 Uvicorn process per container**; horizontal scaling is handled by replica count (pod count), avoiding double-replication that oversells resources.

::: warning Don't use fastapi dev in production
`dev` mode has auto-reload and debugging features — neither performance nor security are suitable for production; production一律 uses `fastapi run` or bare `uvicorn`.
:::

## 22.3 Dockerfile Best Practices

The官方 recommended Dockerfile structure (every line has a reason):

```dockerfile
FROM python:3.13

WORKDIR /code

# ① Copy only the dependency清单 first —— it rarely changes
COPY ./requirements.txt /code/requirements.txt

# ② Then install dependencies —— when the清单 hasn't changed, Docker cache is hit, finishing in seconds
RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt

# ③ Finally copy the business code —— changes most frequently; placing last keeps缓存有效
COPY ./app /code/app

# ④ Must use exec-form CMD (JSON array)
CMD ["fastapi", "run", "app/main.py", "--port", "80", "--proxy-headers"]
```

Four key details:

1. **Layer order is the缓存 strategy**: requirements.txt barely changes — put it first; `app/` changes daily — put it last. Wrong order means reinstalling all dependencies every time you change one line of code.
2. **`--no-cache-dir`** is a pip option that avoids留 the downloaded packages in the image, reducing size.
3. **CMD must use exec form** (`["fastapi", "run", ...]`): shell form (`CMD fastapi run ...`) runs the command inside a shell subprocess, unable to correctly receive SIGTERM signals, breaking graceful shutdown.
4. Companion `.dockerignore` to avoid垃圾 in the image:

```text
.git
__pycache__
*.pyc
.env        # never bake into the image!
docs
tests
.venv
```

Build and run:

```bash
docker build -t myapp .
docker run -d --name mycontainer -p 80:80 myapp
```

## 22.4 Health Checks and Graceful Shutdown

### Health Check Endpoints

Load balancers / K8s need a lightweight endpoint to probe whether the process is alive:

```python
from fastapi import FastAPI

app = FastAPI(lifespan=lifespan)


@app.get("/health", include_in_schema=False)  # doesn't appear in public docs
async def health():
    return {"status": "ok"}
```

Note that liveness probes should be extremely lightweight — don't do heavy database queries inside (probe failure triggers restart, cascading misjudgment); split deep checks into an independent `/ready` readiness probe:

```python
from fastapi import Response, status
from fastapi.responses import JSONResponse
from sqlalchemy import text


@app.get("/ready", include_in_schema=False)
async def ready(response: Response):
    """Readiness probe: check whether real dependencies (database) are available."""
    try:
        engine = app.state.engine
        async with engine.connect() as conn:
            await conn.execute(text("SELECT 1"))
        return {"status": "ready"}
    except Exception:
        # When dependencies are unavailable, don't return 200 — let K8s drain traffic from this instance
        return JSONResponse(status_code=503, content={"status": "not ready"})
```

After deployment you can also write a smoke test script that runs automatically in the release pipeline to verify the new version is truly healthy:

```python
# smoke_test.py —— runs automatically after deployment; rolls back on any failed assertion
import sys
import httpx

BASE = "https://api.example.com"

resp = httpx.get(f"{BASE}/health", timeout=5.0)
assert resp.status_code == 200, f"Health check failed: {resp.status_code}"

resp = httpx.get(f"{BASE}/openapi.json", timeout=5.0)
assert resp.status_code == 200 and "/items/" in resp.text, "OpenAPI docs abnormal"

print("✅ Deployment smoke test passed")
sys.exit(0)
```

### Programmatic Startup and Graceful Shutdown

During rolling releases, old processes要 "finish in-flight requests before exiting." Uvicorn, upon receiving `SIGTERM`, stops accepting new connections and waits for existing requests to complete; the wait上限 is controlled by a parameter:

```bash
uvicorn main:app --timeout-graceful-shutdown 20  # grace up to 20 seconds
```

This is also why CMD must use exec form: PID 1 must directly be the uvicorn process to receive signals; wrapped in a shell, signals are lost and the process can only be force-killed,中断ing in-flight requests.

Besides the CLI approach, you can also programmatically start the production server in Python,方便 embedding custom startup logic:

```python
# serve.py —— python serve.py is equivalent to uvicorn main:app --workers 4
import uvicorn

if __name__ == "__main__":
    uvicorn.run(
        "main:app",
        host="0.0.0.0",
        port=8080,
        workers=4,
        proxy_headers=True,               # trust X-Forwarded-* from Nginx/Traefik
        timeout_graceful_shutdown=20,     # 20-second graceful shutdown grace period
        access_log=False,                 # production can disable access logs, let the proxy record
    )
```

`uvicorn.run()`同样 installs SIGTERM/SIGINT handlers internally: upon receiving a signal, stops accepting new connections → waits for in-flight requests to complete (up to the grace period) → executes the lifespan shutdown段 to release resources → exits. K8s rolling updates正是依赖 this chain to achieve zero-request-loss deployments.

## 22.5 Chapter Summary

- Six deployment要素: HTTPS, auto-start, restart, replicas, memory, pre-steps; HTTPS is handled by the outer TLS termination proxy, Python doesn't handle encryption/decryption;
- Production uses `fastapi run` (not dev); multi-worker leverages multiple cores; quantity tuned by CPU/IO characteristics;单-process-per-container in containers with多-replica scaling;
- Dockerfile黄金顺序: COPY requirements first → install deps → then COPY code; CMD用 exec form to ensure signal receipt;
- `.env` and sensitive信息never go into the image; `.dockerignore` acts as a safety net;
- Provide a `/health` liveness probe; Uvicorn responds to SIGTERM by gracefully draining requests by default; `--timeout-graceful-shutdown` controls the grace period.
