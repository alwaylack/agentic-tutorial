# Chapter 6 · Response Models and Status Codes

> Chapter goals: master response_model's output filtering capability and its security significance, learn input/output model separation, correctly set status codes and document metadata.

## 6.1 Why Response Models Are Needed

Path function return values serialize by default. If database objects carry fields like `password_hash`, `internal_notes`, bare returns are security incidents. `response_model` lets you **declare what clients can see**:

```python
from fastapi import FastAPI
from pydantic import BaseModel, EmailStr

app = FastAPI()


class UserIn(BaseModel):
    # Input model: contains plaintext password (only for registration reception)
    username: str
    email: EmailStr
    password: str


class UserOut(BaseModel):
    # Output model: never contains password
    username: str
    email: EmailStr


@app.post("/user/", response_model=UserOut)
def create_user(user: UserIn):
    # Assume already stored in DB. Here directly returns user with password,
    # but response_model=UserOut filters out the password field
    return user
```

Even if the function returns the complete object, clients only receive `username` and `email`. **Filtering is framework-enforced, not dependent on developer awareness** — this is the security significance of response models.

`response_model` is a **decorator** parameter, not a function parameter — a common beginner mistake.

## 6.2 Return Type Annotation vs response_model

Modern FastAPI supports two declaration methods:

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class Item(BaseModel):
    name: str
    price: float


# Method 1: return type annotation (recommended, editors/static checks recognize it)
@app.get("/items/a", response_model=Item)
def get_a() -> Item:
    return Item(name="pen", price=3.0)


# Method 2: only use return type annotation, FastAPI同样据此生成文档并过滤
@app.get("/items/b")
def get_b() -> Item:
    return Item(name="book", price=42.0)
```

When both exist, **`response_model` takes priority**. This design serves a specific scenario: the function actually returns a database ORM object or dict, different from the declared model type — return type annotation for mypy, `response_model` for FastAPI's "doc + validate + filter":

```python
from typing import Any

@app.get("/db-items/{item_id}", response_model=Item)
def get_db_item(item_id: int) -> Any:
    # Returns SQLAlchemy ORM object, type doesn't match Item,
    # use Any annotation to fool static check, FastAPI still serializes/filter by Item
    return fake_db.get(item_id)
```

## 6.3 Standard Pattern for Input/Output Model Separation

Complete three-model pattern for registration (official tutorial pattern):

```python
from fastapi import FastAPI
from pydantic import BaseModel, EmailStr

app = FastAPI()


class UserIn(BaseModel):
    username: str
    email: EmailStr
    password: str


class UserOut(BaseModel):
    username: str
    email: EmailStr


class UserDB(UserIn):          # Internal model: inherits input model, adds hash field
    password_hash: str


def fake_hash(pwd: str) -> str:
    return "hashed-" + pwd


@app.post("/users/", response_model=UserOut)
def register(user: UserIn):
    db_user = UserDB(
        **user.model_dump(),
        password_hash=fake_hash(user.password),
    )
    # Returned db_user has password and password_hash,
    # but response_model=UserOut only lets through username/email
    return db_user
```

::: tip Don't Use UserIn Directly as Response Model
If `response_model=UserIn`, plaintext password echoes back to the client. Always define different models for "input" and "output," even if fields temporarily match — they evolve independently.
:::

## 6.4 Fine-Grained Output Field Control

`response_model` also supports include/exclude control:

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class Item(BaseModel):
    name: str
    price: float
    description: str | None = None
    tax: float | None = None


items_db = {
    "foo": {"name": "Foo", "price": 50.2, "description": "Special price item", "tax": 5.2},
}


@app.get("/items/{item_id}", response_model=Item)
def read_item(item_id: str):
    return items_db[item_id]


# Only output description and tax fields
@app.get("/items-attrs/{item_id}",
         response_model=Item,
         response_model_include={"description", "tax"})
def read_item_attrs(item_id: str):
    return items_db[item_id]


# Exclude tax field
@app.get("/items-public/{item_id}",
         response_model=Item,
         response_model_exclude={"tax"})
def read_item_public(item_id: str):
    return items_db[item_id]
```

::: warning Applicable boundaries of include/exclude
These parameters suit sporadic tweaks; when field differences are large, still define independent models — models are explicit contracts, include/exclude are implicit patches. Also `response_model_exclude_none=True` automatically omits None-valued fields, useful for saving mobile data.
:::

## 6.5 Status Codes and Document Metadata

Decorator parameters `status_code` sets the success response status code; `tags/summary/description` enrich documentation:

```python
from fastapi import FastAPI, status
from pydantic import BaseModel

app = FastAPI()


class Post(BaseModel):
    title: str
    content: str


@app.post(
    "/posts/",
    status_code=status.HTTP_201_CREATED,   # use 201 for successful creation, not default 200
    tags=["Posts"],
    summary="Create new post",
)
def create_post(post: Post):
    return post


@app.delete("/posts/{post_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_post(post_id: int):
    # 204 means success with no response body, don't return anything
    return None
```

Recommend using named constants from the `status` module rather than magic numbers: `HTTP_201_CREATED`, `HTTP_204_NO_CONTENT`, `HTTP_404_NOT_FOUND`, etc. — the code is documentation.

::: note Status code mnemonic
2xx success (200 default / 201 created / 204 no content); 4xx client error (422 validation failed / 401 unauthorized / 403 forbidden / 404 not found); 5xx server error. In REST design "creation returns 201" is the most commonly overlooked rule.
:::

## 6.6 Chapter Summary

- `response_model`强制过滤输出字段, the framework-level guarantee against sensitive信息泄漏;
- It's a decorator parameter, higher priority than return type annotation, specially for returning ORM/dict scenarios;
- Input model (UserIn) and output model (UserOut) must separate, internal models can inherit input models to extend;
- `response_model_include/exclude/exclude_none` for sporadic tweaks, large differences still use independent models;
- `status_code=status.HTTP_201_CREATED` named constants make status code semantics clear, 201 for creation, 204 for successful deletion.
