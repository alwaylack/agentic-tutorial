## 8.1 Ordinary Functions: The Lightest Custom Tool

Chapter 7 already used ordinary functions as tools; here we补全 engineering details. Function tools support both synchronous and asynchronous definitions:

```python
# custom_func.py —— Both sync and async functions can be tools
import asyncio
import os
import sqlite3
from agno.agent import Agent
from agno.models.openai import OpenAIChat


def get_user(user_id: int) -> dict:
    """Get a user's name and email by user id.

    Args:
        user_id: The numeric id of the user.
    """
    # In real projects this usually queries a database or calls an internal API
    return {"id": user_id, "name": "Gao Tongxue", "email": "gao@example.com"}


async def query_report(report_date: str) -> str:
    """Fetch the daily report content for a given date.

    Args:
        report_date: Date string in YYYY-MM-DD format.
    """
    await asyncio.sleep(0.1)  # Simulate IO
    return f"Daily report for {report_date}: 1024 new users today."


agent = Agent(
    model=OpenAIChat(
        id="deepseek-chat",
        api_key=os.getenv("DEEPSEEK_API_KEY"),
        base_url="https://api.deepseek.com/v1",
    ),
    tools=[get_user, query_report],  # Sync and async can be mixed
)

agent.print_response("Look up user 42's email, then give me the key points from the 2026-01-10 daily report")
```

::: tip Return Value Conventions
Tools can return strings, numbers, dicts, lists — any serializable value. Returning **structured data** (dict/list) is usually better than拼接 long text — the model can更 accurately extract needed fields. If you need to return media files along with text, use `ToolResult`.
:::

## 8.2 @tool Decorator: Adding Behavior Control to Functions

The `agno.tools.tool` decorator (new in v2, continued in 3.x) lets youattach execution policies to tools without changing the function body. The following parameters have all been verified in agno 3.x source:

| Parameter | Default | Description |
|---|---|---|
| `name` / `description` | None | Override the tool name/description visible to the model |
| `show_result` | False | Directly show the result to the user after execution |
| `stop_after_tool_call` | False | Terminate this run after executing this tool |
| `cache_results` / `cache_dir` / `cache_ttl` | False | Result caching with directory and TTL (seconds) |
| `requires_confirmation` | False | Requires human confirmation before execution (expanded in Chapter 21) |
| `pre_hook` / `post_hook` / `tool_hooks` | None | Hooks before/after tool execution |

```python
# tool_decorator.py —— Control tool behavior with @tool
import os
import time
from agno.agent import Agent
from agno.models.openai import OpenAIChat
from agno.tools import tool


@tool(cache_results=True, cache_ttl=300)   # Same input within 5 minutes goes straight to cache
def slow_exchange_rate(base: str, quote: str) -> str:
    """Get the current exchange rate from base currency to quote currency.

    Args:
        base: The base currency code, e.g. USD.
        quote: The quote currency code, e.g. CNY.
    """
    time.sleep(2)  # Simulate expensive third-party API call
    return f"1 {base} = 7.23 {quote}"


@tool(stop_after_tool_call=True, show_result=True)
def submit_ticket(title: str) -> str:
    """Create a support ticket and finish the conversation.

    Args:
        title: Short summary of the issue.
    """
    return f"Ticket #{8848} created: {title}"


agent = Agent(
    model=OpenAIChat(
        id="deepseek-chat",
        api_key=os.getenv("DEEPSEEK_API_KEY"),
        base_url="https://api.deepseek.com/v1",
    ),
    tools=[slow_exchange_rate, submit_ticket],
)

agent.print_response("What is the current USD/CNY exchange rate?")
agent.print_response("Submit a ticket for me: laptop cannot connect to WiFi")
```

The semantics of the two parameters deserve咀嚼:

- **`stop_after_tool_call`**: suitable for "terminal actions". After submitting a ticket there is no need to let the model summarize another round; end the run directly, saving one model call;
- **`show_result`**: suitable for "result is the answer" deterministic outputs (calculators, queries), skipping the model's restatement step.

## 8.3 Toolkit Subclass: Batch-Register a Set of Related Tools

When a business domain has multiple operations and需要共享 state (such as a unified client, auth config), you should写 a Toolkit. The pattern is inheriting `agno.tools.Toolkit` and implementing `__init__`:

```python
# todo_toolkit.py —— Custom to-do Toolkit
import os
from agno.agent import Agent
from agno.models.openai import OpenAIChat
from agno.tools import Toolkit


class TodoTools(Toolkit):
    def __init__(self, **kwargs):
        super().__init__(name="todo_tools", **kwargs)
        self._todos: list[str] = []          # Shared state within the toolkit

        self.register(self.add_todo)
        self.register(self.list_todos)
        self.register(self.remove_todo)

    def add_todo(self, task: str) -> str:
        """Add a task to the todo list.

        Args:
            task: The task description to add.
        """
        self._todos.append(task)
        return f"Added: {task}"

    def list_todos(self) -> str:
        """List all tasks in the todo list."""
        if not self._todos:
            return "List is empty"
        return "\n".join(f"{i + 1}. {t}" for i, t in enumerate(self._todos))

    def remove_todo(self, index: int) -> str:
        """Remove a task by its 1-based index.

        Args:
            index: The 1-based position of the task to remove.
        """
        removed = self._todos.pop(index - 1)
        return f"Removed: {removed}"


agent = Agent(
    model=OpenAIChat(
        id="deepseek-chat",
        api_key=os.getenv("DEEPSEEK_API_KEY"),
        base_url="https://api.deepseek.com/v1",
    ),
    tools=[TodoTools()],
    instructions="Manage the user's to-do list; after adding, deleting, or querying, always展示 the full current list.",
)

agent.print_response("Add three things: buy milk, write weekly report, jog for half an hour")
agent.print_response("Delete item 2")
```

Toolkit construction can also批量 declare control policies by name (also from `Toolkit.__init__` parameters, verified in agno 3.x source): `stop_after_tool_call_tools=["submit_order"]`, `show_result_tools=[...]`, `requires_confirmation_tools=[...]`, and package-level `cache_results=True`. These have the same effect as the decorators in 8.2, just at the Toolkit dimension.

## 8.4 Exception Handling Inside Tools

Tools访问外部世界, so failures are the norm. Agno catches exceptions thrown by tools and passes the error信息 back to the model, letting the model decide whether to retry or take another path; you can also do统一兜底 via `tool_hooks`:

```python
# safe_tools.py —— Exception fallback example
import os
from agno.agent import Agent
from agno.models.openai import OpenAIChat
from agno.tools import tool


def retry_on_error(func_name: str, func, *args, **kwargs):
    """post_hook style fallback: log and transform exceptions."""
    try:
        return func(*args, **kwargs)
    except Exception as e:
        # Error messages returned to the model should be "actionable": tell it what to do next
        return f"Call failed ({type(e).__name__}): {e}. Please check parameters and retry once."


@tool(post_hook=retry_on_error)
def divide(a: float, b: float) -> float:
    """Divide a by b.

    Args:
        a: Numerator.
        b: Denominator, must not be zero.
    """
    return a / b   # ZeroDivisionError when b=0 is caught by the hook


agent = Agent(
    model=OpenAIChat(
        id="deepseek-chat",
        api_key=os.getenv("DEEPSEEK_API_KEY"),
        base_url="https://api.deepseek.com/v1",
    ),
    tools=[divide],
)

agent.print_response("Calculate the result of 10 divided by 0")
```

> Heuristic: error messages for "humans" and for "models" should be designed separately. Errors to the model should clearly state **what to do next** ("please check parameters", "no data for that city, please try another"), rather than堆 a stack trace.

## 8.5 Tool Design Granularity Principles

Two extremes beginners最容易犯:

- ❌ **Granularity too fine**: `get_id`, `get_name`, `get_email` as three tools; the model needs multiple rounds to拼凑;
- ❌ **Granularity too coarse**: one `manage_company(query: str)`万能接口; vague schema leads to model passing parameters乱传.

The recommended approach is **task-oriented modeling**: one tool completes one完整的事 from the model's perspective, with as few and明确 parameters as possible. Contrast:

```python
# granularity.py —— Task-oriented vs database-oriented
def get_weather_bad(city: str, field: str) -> str:
    """Get one field of weather. BAD: model must先guess field values."""


def get_weather_good(city: str) -> dict:
    """Get current weather summary (temperature, condition, humidity) for a city.

    Args:
        city: City name in Chinese or English.
    """
    # Return structured full fields in one go; model picks what it needs
    return {"city": city, "temperature": 26, "condition": "cloudy", "humidity": 62}
```

Additionally, two production rules:

1. **Separate idempotent from side-effect**: read-only tools can be called freely; side-effect tools (placing orders, sending emails) must配 `requires_confirmation=True` or rate-limiting;
2. **Resolve timeouts and retries inside the tool**: do not指望 the model to handle network flakiness itself.

## 8.6 Chapter Summary

- Three custom styles: ordinary functions (lightest), `@tool` decorator (attach execution policies), `Toolkit` subclass (shared state + batch registration);
- `@tool` core parameters: `cache_results` caching, `stop_after_tool_call` terminate run, `show_result` direct output, `requires_confirmation` human confirmation;
- Toolkit can批量 declare strategies by name with `*_tools` list parameters;
- Tool exceptions are caught by Agno and passed back to the model; error文案 should be written as "actionable" guidance;
- Tools designed按任务 granularity: one call solves one complete问题, returning structured data.
