## 6.1 Agno's Three-Layer Prompt System

Agno does not ask you to hand-write a large system prompt; instead it splits it into structured configuration items. According to the official Context Engineering model:

| Configuration | Layer | Role |
|---|---|---|
| `description` | Highest | Who the Agent is, overall responsibilities — like a "job description" |
| `instructions` | Middle | List of specific behavioral rules — like an "operations manual" |
| `system_message` | Override | Fully custom system message; once set, **replaces** automatic assembly of the above two |

```python
# prompt_layers.py —— Usage of the three-layer system
import os
from dotenv import load_dotenv
from agno.agent import Agent
from agno.models.openai import OpenAIChat

load_dotenv()
model = OpenAIChat(
    id="deepseek-chat",
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com/v1",
)

agent = Agent(
    model=model,
    # Job description: one sentence clarifying role and boundaries
    description="You are a rigorous Python technical interviewer.",
    # Operations manual: list behavioral rules one by one; Agno numbers them before injecting into system message
    instructions=[
        "Ask only one question at a time, wait for the candidate's answer before following up",
        "Follow-up questions should target weaknesses in the previous round's answer",
        "Use Chinese throughout; code examples may use English identifiers",
        "Do not give the answer directly; guide the candidate to think first",
    ],
    markdown=True,
)

agent.print_response("Start the interview with me")
```

**Why use a list instead of one big paragraph?** A list makes each rule an independent line; the model's compliance rate for "itemized instructions" is significantly higher than for long paragraphs. At the same time it便于 code review and version diff — this is the key to managing prompts as "configuration" rather than "copywriting".

## 6.2 instructions Support Template Variables

Placeholders can be put in instructions, combined with session state to fill at runtime, achieving "one set of prompts serving multiple users":

```python
# prompt_template.py —— Template variable injection
agent = Agent(
    model=model,
    db=None,
    instructions=[
        "The user's current membership level is {plan}; adjust tone accordingly",
        "When recommending plans to free users, must explain paid feature limitations",
    ],
    session_state={"plan": "pro"},     # Values from session state fill into {plan}
)

# Same Agent serving different-tier users with a different session_state
agent.print_response("What features are available?", session_state={"plan": "free"})
```

This approach decouples "business data" from prompt text: changing membership rules only touches `session_state`, not the prompts.

## 6.3 When to Use system_message

For the vast majority of scenarios, `description + instructions` is sufficient. Only use `system_message` when you need **complete control over the system message原文** — note that it bypasses automatic assembly:

```python
# system_message_demo.py —— Fully overriding system message
agent = Agent(
    model=model,
    description="This field will be ignored",           # ⚠️ Ineffective after setting system_message
    instructions=["Nor will this take effect"],
    system_message="You are pirate Translator, translating user input into pirate-style English.",
)
```

::: warning Recommendation
Unless migrating legacy systems or interfacing with strongly-constrained third-party prompt specs, **do not use `system_message`**. Giving up structured layering is giving up Agno's fine-grained context management.
:::

## 6.4 Few-shot Example Injection

If you want output format to be extremely stable, the most effective means is to provide examples in the instructions (few-shot). Combined with the structured output from Chapter 5, format is guaranteed by schema; **style and judgment criteria** rely on examples:

```python
# few_shot.py —— Anchoring classification criteria with examples
from pydantic import BaseModel, Field
from typing import Literal

class TicketCategory(BaseModel):
    category: Literal["bug", "feature", "question", "complaint"]
    urgency: int = Field(ge=1, le=5, description="Urgency level")

support_router = Agent(
    model=model,
    description="Customer service ticket classifier.",
    instructions=[
        "Output category and urgency (1-5) based on ticket content",
        "Judgment criteria examples:",
        '- "Login button does nothing when clicked" → bug, urgency=3',
        '- "Hope to add a dark mode" → feature, urgency=2',
        '- "Will data be leaked?" → question, urgency=1',
        '- "If not resolved I will complain to the consumer association!" → complaint, urgency=5',
    ],
    output_schema=TicketCategory,
)

cases = ["App crashed and cannot open at all", "Can you release a WeChat mini-program version?"]
for c in cases:
    r = support_router.run(c)
    print(c, "->", r.content.category, r.content.urgency)
```

The value of examples lies in **eliminating ambiguity in standards**: is "crash" a bug or a complaint? With对照 examples, the model's choice becomes much more stable.

## 6.5 Chinese Prompt Best Practices

The tutorial uniformly uses Chinese models and Chinese scenarios. Several empirically effective experiences:

1. **Prompt language matches business language**: when having DeepSeek handle Chinese tasks, write prompts in Chinese too — terminology understanding is more accurate;
2. **Avoid long negative sentences**: "Do not use complex sentence structures" is worse than directly writing "Each sentence no more than 25 characters";
3. **Keep rule count under 10**: beyond that middle clauses are easily ignored; better to split into multiple specialized Agents;
4. **Put critical format requirements at beginning and end**: compliance rate for the first and last items is highest; place hard format constraints at these positions;
5. **Use `additional_guidance` to supplement temporary rules** (if dynamic behavioral requirements need to be appended), keeping main instructions stable for effect comparison.

## 6.6 Iteration Method: Test Prompts Like Code

The correct posture for prompt engineering is not "tweak by feel"; instead build a small eval set for regression verification:

```python
# prompt_eval.py —— Minimal prompt regression test
EVAL_CASES = [
    ("Login page white screen", "bug"),
    ("Hope to support Excel export", "feature"),
    ("How to change bound phone number", "question"),
]

def evaluate(agent) -> float:
    hits = sum(
        agent.run(q).content.category == expect
        for q, expect in EVAL_CASES
    )
    return hits / len(EVAL_CASES)

print(f"Accuracy: {evaluate(support_router):.0%}")
# Run once before and once after modifying instructions; adopt the new version based on numbers
```

Extending this approach to dozens of cases and integrating into CI for regular runs is the precursor to the evaluation system (Evals) in Chapter 25.

## 6.7 Chapter Summary

- `description` sets role, `instructions` sets rules, `system_message` fully overrides (use with caution);
- instructions use itemized lists + template variables `{placeholder}`; they are maintainable "configuration" not copy;
- Few-shot examples eliminate ambiguity in judgment criteria and output style; best used配合 with output_schema;
- Chinese prompts: prompt and business in same language, few negations, rules ≤10, hard constraints at beginning/end;
- Prompt changes must be verified quantitatively with eval sets; do not ship based on feel.
