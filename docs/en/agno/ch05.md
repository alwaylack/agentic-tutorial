# Chapter 5 · Structured Output output_schema

> Chapter goals: transform the Agent's output from "free-form text" to "validated Pydantic objects", master the usage, principles, and design techniques of output_schema.

## 5.1 The Pain Points of Free-Form Text

Suppose you are building a "movie recommendation Agent" and want downstream code to read the recommendation results. If the model returns a prose paragraph, you have to write regex or `json.loads` to parse it — the model occasionally misses a quote mark or adds explanatory text, and the program crashes outright. **Structured output** eliminates this problem completely: you define the data structure, the model fills it in, and the framework validates it.

## 5.2 Basic Usage: output_schema + Pydantic

```python
# structured_basic.py —— Make the Agent return a Pydantic object
import os
from dotenv import load_dotenv
from pydantic import BaseModel, Field
from agno.agent import Agent
from agno.models.openai import OpenAIChat

load_dotenv()

class MovieScript(BaseModel):
    setting: str = Field(description="The location where the story takes place")
    genre: str = Field(description="Movie genre")
    storyline: str = Field(description="Plot summary in three sentences or less")

agent = Agent(
    model=OpenAIChat(
        id="deepseek-chat",
        api_key=os.getenv("DEEPSEEK_API_KEY"),
        base_url="https://api.deepseek.com/v1",
    ),
    output_schema=MovieScript,     # Key: declare the output structure
)

response = agent.run("Write a heist movie idea set in Tokyo")

print(type(response.content))          # <class 'MovieScript'>, not a string!
print(response.content.setting)        # Access directly via attributes
print(response.content.genre)
print(response.content.storyline)
```

`response.content` is directly a `MovieScript` instance — field access has type hints, IDE auto-completion, and misspelled field names error immediately.

## 5.3 Underlying Principles: Schema Injection and Validation Fallback

Understanding the principle is the key to troubleshooting. After setting `output_schema`, Agno does four things:

1. Converts the Pydantic model to a **JSON Schema**;
2. If the model supports native structured output protocols (such as OpenAI's JSON Schema mode), the constraint is sent directly;
3. If not supported, the schema is written into the prompt and the model is required to output JSON, which is then parsed;
4. The parsed result is **validated** by Pydantic; on failure an error is recorded — at this point `content` may degrade to a raw string.

::: warning Mandatory Defense
Third-party models such as DeepSeek mostly take the "prompt + parsing" path, with occasional parsing failures. The official documentation explicitly recommends: **check the type of `content` before accessing schema fields**.

```python
# safe_access.py —— Type defense
result = agent.run("Write another space opera idea")
if isinstance(result.content, MovieScript):
    print("Structured successfully:", result.content.genre)
else:
    print("Parsing failed, raw content:", result.content)   # Fallback handling
```
:::

## 5.4 Advanced: Nested Models, List Fields, and Per-Call Override

Real-business output structures are often nested. Pydantic's composition capabilities are fully applicable here:

```python
# structured_nested.py —— Nested structure and runtime override
from pydantic import BaseModel, Field
from agno.agent import Agent
from agno.models.openai import OpenAIChat
import os
from dotenv import load_dotenv

load_dotenv()
model = OpenAIChat(
    id="deepseek-chat",
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com/v1",
)

class Ingredient(BaseModel):
    name: str = Field(description="Ingredient name")
    amount: str = Field(description="Amount, e.g. 200g")

class Recipe(BaseModel):
    title: str
    difficulty: str = Field(description="Choose one: easy/medium/hard")
    ingredients: list[Ingredient] = Field(description="Ingredient list")   # Nested list
    steps: list[str] = Field(description="Steps list")

agent = Agent(model=model)   # Do not specify schema at construction

# Specify different schemas per call for the same Agent —— one Agent serves multiple output formats
recipe = agent.run("Design a tomato beef brisket recipe that takes 20 minutes", output_schema=Recipe).content
print(recipe.title, "has", len(recipe.ingredients), "ingredients")
for ing in recipe.ingredients:
    print(f"- {ing.name}: {ing.amount}")
```

Per-call override (`run(..., output_schema=...)`) is ideal for "one Agent, multiple tasks" scenarios, avoiding cloning an Agent for each output format.

## 5.5 Comparison with Hand-Written Parsing + Integration with Tools

Compare with the old hand-written parsing approach, and you will understand the value of structured output:

```python
# old_way.py —— Anti-pattern: hand-written JSON parsing
import json

resp = agent.run("Return the recipe in JSON format, fields include title, ingredients, steps")
try:
    # The model often wraps the JSON with "Okay, here is..." — direct crash
    data = json.loads(resp.content)
except json.JSONDecodeError as e:
    print("Parsing failed, need hand-written cleanup logic:", e)
    # So you start stripping backticks, regex extraction of {...}, retries...
```

Structured output also coexists with tools: the Agent first calls tools to fetch data, then organizes the answer according to the schema. The official example is stock analysis — tools fetch real-time prices, and the `StockAnalysis` model constrains the fields of the final conclusion. This "**free process, constrained conclusion**" pattern is a common architecture for production-grade Agents.

## 5.6 Schema Design Tips

Combining official recommendations, four practical lessons:

1. **Write `Field(description=...)` for every field** — the description is the requirement specification to the model; the more specific, the more stable;
2. **Express enumerations with constraints**: `Field(description="must be one of buy/hold/sell")` or `Literal["buy", "hold", "sell"]`;
3. **Use `ge/le` for numeric ranges**: e.g. `confidence: float = Field(ge=0, le=1)`; the validation layer automatically intercepts out-of-range values;
4. **Avoid excessively deep nesting** (recommended ≤3 levels): the deeper the layers, the higher the format error rate of third-party models.

## 5.7 Chapter Summary

- `output_schema` changes `content` from a string to a validated Pydantic object;
- The principle is "JSON Schema injection → generation → Pydantic validation"; third-party models may fall back to prompt parsing;
- Use `isinstance` to defend against parsing failures before accessing fields;
- Schema can be omitted at construction and passed per-call at runtime; one Agent adapts to multiple outputs;
- The clearer the field descriptions, the more stable the output.
