# Chapter 5 · Structured Output with output_schema

> Chapter goals: Transform the Agent's output from "free text" to "validated Pydantic objects", mastering the usage, principles, and design techniques of output_schema.

## 5.1 The Pain Points of Free Text

Suppose you're building a "movie recommendation Agent" where downstream code reads the recommendation results. If the model returns a prose paragraph, you'd need to write regex or `json.loads` to parse it—the model occasionally misses a quote or adds explanatory text, and the program crashes directly. **Structured output** completely eliminates this problem: you define the data structure, the model fills it in, and the framework validates it.

## 5.2 Basic Usage: output_schema + Pydantic

```python
# structured_basic.py -- Make the Agent return a Pydantic object
import os
from dotenv import load_dotenv
from pydantic import BaseModel, Field
from agno.agent import Agent
from agno.models.openai import OpenAIChat

load_dotenv()

class MovieScript(BaseModel):
    setting: str = Field(description="The location where the story takes place")
    genre: str = Field(description="Movie genre")
    storyline: str = Field(description="Plot summary in three sentences or less")

agent = Agent(
    model=OpenAIChat(
        id="deepseek-chat",
        api_key=os.getenv("DEEPSEEK_API_KEY"),
        base_url="https://api.deepseek.com/v1",
    ),
    output_schema=MovieScript,     # Key: declare output structure
)

response = agent.run("Write a movie idea about a heist set in Tokyo")

print(type(response.content))          # <class 'MovieScript'>, not a string!
print(response.content.setting)        # Access directly via attributes
print(response.content.genre)
print(response.content.storyline)
```

`response.content` is directly a `MovieScript` instance—field access has type hints, IDE autocomplete, and misspelled field names throw errors immediately.

## 5.3 Underlying Principles: Schema Injection and Validation Fallback

Understanding the principles helps troubleshoot issues. After setting `output_schema`, Agno does four things:

1. Converts the Pydantic model to **JSON Schema**;
2. If the model supports native structured output protocol (such as OpenAI's JSON Schema mode), directly issues the constraint;
3. If not supported, writes the schema into the prompt and requires JSON output, then parses;
4. Uses Pydantic **validation** on the parsed result; on failure, logs the error—此时 `content` may degrade to the original string.

::: warning Must-do Defense
Third-party models like DeepSeek mostly follow the "prompt + parsing" path, with occasional parsing failures. The official documentation explicitly recommends: **check the type of `content` before accessing schema fields**.

```python
# safe_access.py -- Type defense
result = agent.run("Write another space opera idea")
if isinstance(result.content, MovieScript):
    print("Structured success:", result.content.genre)
else:
    print("Parsing failed, raw content:", result.content)   # Fallback handling
```
:::

## 5.4 Advanced: Nested Models, List Fields, and Per-Run Override

Real-world business output structures are often nested. Pydantic's composition capabilities work perfectly here:

```python
# structured_nested.py -- Nested structures and runtime override
from pydantic import BaseModel, Field
from agno.agent import Agent
from agno.models.openai import OpenAIChat
import os
from dotenv import load_dotenv

load_dotenv()
model = OpenAIChat(
    id="deepseek-chat",
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com/v1",
)

class Ingredient(BaseModel):
    name: str = Field(description="Ingredient name")
    amount: str = Field(description="Quantity, e.g., 200g")

class Recipe(BaseModel):
    title: str
    difficulty: str = Field(description="Choose one: easy/medium/hard")
    ingredients: list[Ingredient] = Field(description="Ingredient list")   # Nested list
    steps: list[str] = Field(description="Steps list")

agent = Agent(model=model)   # Don't specify schema at construction

# Specify different schemas per run with the same Agent -- one Agent serves multiple output formats
recipe = agent.run("Design a tomato beef dish that can be completed in 20 minutes", output_schema=Recipe).content
print(recipe.title, "has", len(recipe.ingredients), "ingredients in total")
for ing in recipe.ingredients:
    print(f"- {ing.name}: {ing.amount}")
```

Per-run override (`run(..., output_schema=...)`) is very suitable for "one Agent, multiple tasks" scenarios, avoiding cloning an Agent for each output format.

## 5.5 Comparison with Hand-written Parsing + Integration with Tools

Compare with the old hand-written parsing approach, and you'll understand the value of structured output:

```python
# old_way.py -- Negative example: hand-written JSON parsing
import json

resp = agent.run("Return a recipe in JSON format with fields including title, ingredients, steps")
try:
    # The model often wraps a sentence like "Okay, here's..." around the JSON, which crashes directly
    data = json.loads(resp.content)
except json.JSONDecodeError as e:
    print("Parsing failed, need hand-written cleaning logic:", e)
    # So you start striping backticks, regex extracting {...}, retrying...
```

Structured output also supports coexisting with tools: the Agent calls tools to fetch data first, then organizes the answer according to the schema. The official example is stock analysis—the tool queries real-time stock prices, and the `StockAnalysis` model constrains the final conclusion's fields. This "**process is free, conclusion is constrained**" pattern is a common architecture for production-grade Agents.

## 5.6 Schema Design Techniques

Combining official recommendations, four practical experiences:

1. **Write `Field(description=...)` for every field**—the description is the requirement specification for the model, the more specific the more stable;
2. **Use constraints to express enums**: `Field(description="Must be one of buy/hold/sell")` or `Literal["buy", "hold", "sell"]`;
3. **Use `ge/le` for numeric ranges**: e.g., `confidence: float = Field(ge=0, le=1)`, the validation layer automatically intercepts out-of-range values;
4. **Avoid deeply nested structures** (recommended ≤3 levels): the deeper the layers, the higher the format error rate from third-party models.

## 5.7 Chapter Summary

- `output_schema` transforms `content` from a string to a validated Pydantic object;
- The principle is "JSON Schema issuance → generation → Pydantic validation"; third-party models may fall back to prompt parsing;
- Use `isinstance` defense before accessing fields to handle parsing failures;
- Schema can be omitted at construction and passed per-run at runtime, one Agent adapts to multiple outputs;
- The clearer the field descriptions, the more stable the output.
