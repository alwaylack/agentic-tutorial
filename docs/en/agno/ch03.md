# Chapter 3 · Running Agents and Parsing RunOutput

> Chapter goals: master the differences between `run()/arun()/print_response()` three running methods, learn to extract content, messages and metrics from `RunOutput`, and understand the correct posture for multi-turn conversations.

## 3.1 Three Running Methods

Agno's official documentation gives clear advice on running methods: **use `print_response()` for development/debugging, use `run()` or `arun()` for production code**.

```python
# run_basics.py
import os
from dotenv import load_dotenv
from agno.agent import Agent
from agno.models.openai import OpenAIChat

load_dotenv()

agent = Agent(
    model=OpenAIChat(
        id="deepseek-chat",
        api_key=os.getenv("DEEPSEEK_API_KEY"),
        base_url="https://api.deepseek.com/v1",
    ),
)

# Method 1: Print directly during development, human-readable, but no return value
agent.print_response("Explain dependency injection in one sentence")

# Method 2: Synchronous run, returns RunOutput object — use this for business code
response = agent.run("Explain closures in one sentence")
print(response.content)      # The actual answer text is here

# Method 3: Asynchronous run (coroutine), suitable for high-concurrency servers
import asyncio

async def main():
    resp = await agent.arun("Explain decorators in one sentence")
    print(resp.content)

asyncio.run(main())
```

`print_response` internally also calls `run`; it just additionally handles formatted printing. When writing unit tests or web interfaces, you must use `run/arun` because you need to assert or process the return value.

## 3.2 RunOutput Core Fields

The return value of `run()` is a `RunOutput` object. The core attributes defined by the official documentation are as follows:

| Field | Meaning |
|---|---|
| `content` | Final answer content (string; Pydantic object when structured output) |
| `messages` | Complete message list sent to the model this time (including system/tool messages) |
| `metrics` | Token usage, duration and other metrics |
| `run_id` / `session_id` | Unique ID for this run and the所属 session ID |
| `agent_id` / `agent_name` | Agent identifier that ran this request |
| `reasoning_content` | Reasoning process text for reasoning models |

```python
# inspect_output.py —— Inspect RunOutput fields
import os
from dotenv import load_dotenv
from agno.agent import Agent
from agno.models.openai import OpenAIChat

load_dotenv()
agent = Agent(model=OpenAIChat(
    id="deepseek-chat",
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com/v1",
))

r = agent.run("What is idempotency?")

print("Answer:", r.content[:80], "...")
print("run_id:", r.run_id)
print("Message count:", len(r.messages))
for m in r.messages:
    print("-", m.role, ":", str(m.content)[:50])
print("Input tokens:", r.metrics.input_tokens, "/ Output tokens:", r.metrics.output_tokens)
```

::: tip What is metrics useful for
`metrics` is the foundation for cost accounting: record the token count for each run, and you can stat expenses by user/feature dimension at month end. Chapter 24's observability will expand on this systematically.
:::

## 3.3 Multi-turn Conversations: Why the Second Run "Forgets"

First, look at a pitfall every beginner steps into:

```python
# memory_trap.py —— Demonstrate default no-memory behavior
agent = Agent(model=make_model())   # make_model see section 2.3

agent.run("My name is Gao Xiaoling, and my favorite number is 7")
resp = agent.run("What is my name?")   # ❌ Model cannot answer!
print(resp.content)
```

There is no shared state between two `run()` calls: each invocation is an independent new context, and the model has no idea what was said last time. There are three solutions, with increasing complexity:

1. **Manually concatenate history**: Add the previous Q&A to the next input yourself;
2. **Chat history**: Let Agno automatically carry the same session's historical runs (requires配合 storage, Chapters 14–15);
3. **Memory**: Cross-session user-level memory (Chapter 16).

This section uses the most naive manual method first to clarify the concept:

```python
# manual_history.py —— Manually maintain conversation history
history = []

def chat(question: str) -> str:
    prompt = ""
    for q, a in history:                       # Concatenate history into prompt
        prompt += f"User: {q}\nAssistant: {a}\n"
    prompt += f"User: {question}"
    resp = agent.run(prompt)
    history.append((question, resp.content))   # Record this round's result
    return resp.content

chat("My favorite color is blue")
print(chat("What color do I like?"))                 # ✅ Can answer blue
```

The problems with this写法 are obvious: prompts get longer and longer, token costs rise linearly, and persistence is impossible. So it only suits understanding the principle; for production environments, please use the session mechanism in Chapter 14.

## 3.4 Asynchronous Concurrent Running of Multiple Agents

The value of `arun` only shows in concurrent scenarios: three independent tasks run serially requires three network round-trips; asynchronous concurrency needs only the slowest one's time:

```python
# concurrent_runs.py —— asyncio.gather concurrent three requests
import asyncio
import os
from dotenv import load_dotenv
from agno.agent import Agent
from agno.models.openai import OpenAIChat

load_dotenv()
agent = Agent(model=OpenAIChat(
    id="deepseek-chat",
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com/v1"),
)

async def main():
    questions = ["Explain the difference between threads and processes", "Explain the difference between TCP and UDP", "Explain the difference between GET and POST"]
    # Three requests sent simultaneously, gather collects all results
    results = await asyncio.gather(*(agent.arun(q) for q in questions))
    for q, r in zip(questions, results):
        print(f"[{q}] -> {r.content[:40]}...")

asyncio.run(main())
```

Note the generator expression in `asyncio.gather`: create a coroutine for each question. If a request fails, the entire gather throws an exception; in production, use `return_exceptions=True` to handle failures individually.

## 3.5 Chapter Summary

- Use `print_response` for development/debugging, `run` for business code, `arun` for concurrent scenarios;
- `RunOutput` key information: `content` for answers, `messages` for context, `metrics` for cost calculation;
- By default, each `run()` is independent; the model has no cross-call memory;
- Manually concatenating history enables multi-turn but at high cost; the correct solution is session storage + chat history (Chapters 14–15).
